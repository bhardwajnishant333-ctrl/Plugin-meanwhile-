**Meanwhile:**
**Your migration can move every byte perfectly and still leave you with wrong indexes, and Postgres won't tell you.**

When Postgres sorts text, it hands the comparison to the operating system's C library (glibc). The B-tree on a `text` column is laid out in whatever order glibc used when the index was built. pgBackRest restores files physically, and pg_upgrade keeps indexes as they are, so your indexes arrive in the order of the *old* machine's glibc. In glibc 2.28 (2018), the sorting rules for most locales were rewritten. Spaces, hyphens and punctuation moved around the most. So on a new glibc, an index built under the old one can be in the wrong order for queries running now. Lookups miss rows that exist. Unique constraints can let duplicates in. Nothing crashes.

Which side of that line you're on depends on the base OS of your old VMs versus your new Percona images. I'm not sure what the current images ship, so check: `ldd --version` in both places. As I remember it, Postgres 15+ records a database collation version and warns on a mismatch. Older releases mostly didn't, so when you're starting from 13, don't count on a warning.

**Twist:** this isn't data corruption in the usual sense. Every byte arrives intact. What broke is an assumption: text order was always an outside dependency that just never changed. Moving into containers is exactly when the OS under the database gets swapped. If the glibc versions differ, `REINDEX` the text indexes (or check them first with the `amcheck` extension) before you let traffic in.

**Meanwhile:**
**The most famous problem in distributed systems is named after Byzantium for a fairly silly reason: nobody was left to be offended.**

Leslie Lamport, Robert Shostak and Marshall Pease published "The Byzantine Generals Problem" in 1982. The setup: generals surround a city and have to agree to attack or retreat, sending messages by runner, and some of the generals are traitors who lie. Lamport has written that he took the idea of a memorable story from Dijkstra's "Dining Philosophers". His first name for it was the "Albanian Generals", because Albania was a closed-off country back then. A colleague pointed out that there are Albanians outside Albania. So Lamport switched to Byzantium, an empire whose citizens are no longer around to complain.

The result is a real number. When generals can lie and messages can't be verified, tolerating *f* traitors takes at least **3f + 1** generals. With 3 generals and 1 traitor, agreement is impossible. If messages are signed so nobody can forge them, the bound goes away.

**Twist:** most real systems quietly don't pay for this. Raft and Paxos, used by etcd and therefore by Kubernetes itself, assume nodes crash but never lie. That brings the price down to **2f + 1**. The extra *f* nodes are what it costs to defend against lying. Your new cluster's failover sits on that cheaper assumption. As far as I know, Percona's operator runs Patroni on top of the Kubernetes API, which is backed by etcd. That's fine as long as the failure looks like a dead node, not a node that confidently reports wrong state.

2) **Sideways:** the real Byzantine diplomatic service, which reportedly paid neighboring peoples to fight each other instead of fighting them itself
3) **Wildcard:** the "two generals problem", a simpler cousin with no traitors at all, that is still provably unsolvable

**Two honest generals with one unreliable messenger can never be sure they agree, and this can be proved.**

Two armies sit on hills on opposite sides of a valley. They win only if both attack at once. The only way to talk is a runner through the valley, and runners can be captured. A sends "attack at dawn." B replies "got it." But B can't attack yet, because A doesn't know the reply arrived. So A confirms the confirmation, and now A is the one left unsure. The proof is short. Suppose some protocol works, and take the shortest one. Its last message might be lost, so the sender can't make their decision depend on it arriving. Then you could drop that message and the protocol would still work, which means it wasn't the shortest. So no fixed number of messages can make both sides certain. The problem was described in 1975 by Akkoyunlu, Ekanadham and Huber. Jim Gray gave it the "generals" name in 1978.

**Twist:** you meet this one every day. If the connection drops while Postgres is answering a `COMMIT`, the client can't tell whether the transaction committed. The database knows; the client doesn't, and no retry design fully fixes that. Real systems don't solve the problem. They live with it, using timeouts, retries and writes that are safe to repeat. One idempotency key works better than any number of confirmations.

2) **Sideways:** how TCP's three-way handshake lives with the problem without solving it
