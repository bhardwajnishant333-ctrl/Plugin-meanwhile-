**"uv is fast because it's written in Rust" is mostly a myth.**

Poetry and uv use the same resolver algorithm. Both are built on PubGrub, which Natalie Weizenbaum designed for Dart's package manager in 2018. Poetry has its own Python port, and uv uses the Rust crate `pubgrub`. Most of uv's speed comes from avoiding work, not from doing the same work faster:

- **It barely downloads anything to resolve.** The resolver needs each wheel's dependency metadata. When the index offers that metadata as a separate file (PEP 658), uv fetches just that. When it doesn't, uv uses HTTP range requests to read the end of the zip, find the `METADATA` entry, and fetch only those bytes. The rest of the wheel is never downloaded.
- **Installs are mostly links, not copies.** uv keeps one global cache and links packages into your venv from it: hardlinks on Linux, copy-on-write clones on macOS. A "fresh" install can be close to free.
- **Downloads and builds run in parallel.**

**The twist:** most of the speed comes from filesystem tricks, so it can quietly disappear. In Docker, if the uv cache and the venv are on different filesystems (like a cache mount and the image layer), hardlinks fail. uv warns `Failed to hardlink files; falling back to full copy` and keeps going, just slower. Setting `UV_LINK_MODE=copy` stops the warning. It doesn't bring the speed back, but it makes the behavior explicit. That's worth checking when Claude touches your Dockerfile.

**Meanwhile:**
**Picasso's best-known color linocuts were made from a single block that no longer exists in any form that could print them again.**

The reduction method, also called the "suicide print," works like this:
- **One block, many colors, in order.** Carve away what should stay white and print the lightest color on every sheet. Then carve away whatever should keep that first color, re-ink the same block in the next color, and print over the same sheets. Repeat from light to dark.
- **Every cut destroys the previous state.** By the final color, most of the block is gone. You can't print more of color one, ever.
- **The edition is fixed at the first pass.** Every sheet you'll ever have is printed in color one. A misregistered sheet later on is simply lost, so editions only shrink.

Picasso took this up in the late 1950s in Vallauris, working with the local printer Hidalgo Arnéra. *Bust of a Woman after Cranach the Younger* (1958) and *Still Life under the Lamp* (1962) are well-known results. Accounts differ on why he chose reduction over separate blocks for each color. Lining up multiple blocks is fiddly, and he liked working fast and committing. I'm not certain which reason mattered more.

**The twist:** the block's history survives only in the prints. Each sheet is a full log of every state the block went through, and the block itself ends up as just the final layer. It's version control turned inside out: the prints keep the history, and the block keeps only the latest version. That's also why reduction printers over-print the first color and pull proofs between states. You can't roll back, so you make extra copies before each cut.

**Quickest fix (stay on Flask 2.2):**
```bash
uv add "werkzeug<3"
uv sync
uv run flask --version
```

**Better long-term fix (upgrade Flask):**
```bash
uv add "flask>=3.0"
uv sync
```
Flask 3 needs Werkzeug 3 and is the supported line. Flask 3.0 mostly removes things that 2.3 had already deprecated, so check your app for warnings before you switch.
