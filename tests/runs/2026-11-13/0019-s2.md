Halfway through your port, a leftover `.button {}` rule with one class selector will beat `bg-blue-500` every time. Specificity has nothing to do with it.

**Why:** Tailwind v4 puts all of its output into native CSS cascade layers: `@layer theme, base, components, utilities`. The cascade checks layers before it checks specificity, and styles outside any layer beat styles inside every layer. Your CSS Modules files aren't in a layer, so every leftover module rule outranks every Tailwind utility, even an ID-heavy selector against a single class. It looks like random override bugs while the code is half-migrated.

**Twist:** `!important` flips the order. For important declarations, layered styles beat unlayered ones, and earlier layers beat later ones. So `!bg-red-500` (Tailwind's important modifier) beats a module's plain rule, and also beats an unlayered `!important`. Two override systems that rank in opposite directions are in your codebase right now.

The practical fix: wrap the legacy modules in `@layer legacy` and declare that layer before `utilities`. Then Tailwind wins by default, and you can delete the modules one at a time.

**Meanwhile:**
One of the hardest tasks in chess problems took composers about a century to solve, and the solution was only a mate-in-4.

**What it is:** In the Babson task, Black can promote a pawn to a queen, rook, bishop or knight. In each line, White's only winning reply is to promote to the same piece. So Black's queen gets answered by White's queen, Black's knight by White's knight, and so on. It's named after Joseph Ney Babson, the American composer who posed the idea in the late 1800s. I'm not sure of the exact year. Over the following decades composers got versions to work in less strict forms, such as selfmates. The standard direct-mate version held out until Leonid Yarosh published one in 1983, as a mate-in-4.

**Why it's so hard:** Four promotions are easy. Making each one forced is not. In every line, the other three White promotions have to fail, so that's 12 tries that need a specific refutation. Each underpromotion also needs its own reason:
- A **bishop** promotion usually works because a queen would give stalemate.
- A **rook** promotion is the same idea along a different line.
- A **knight** promotion needs a check or a fork that no other piece can give.

So you're really building four different stalemate or check mechanisms on one board, and they can't spoil each other.

**Twist:** That's a 4×4 matrix with exactly 4 cells true, which is exhaustive case analysis. The hard work in a problem goes into the moves that have to fail. That fits your port too: the component variants you have to rule out are what make the API.

As far as I know, no orthodox Babson exists in fewer than 4 moves. I'm not certain, but if you're a mate-in-3 composer, that's worth checking.

**Meanwhile:**
In 1782 Euler guessed that a certain kind of grid couldn't exist for infinitely many sizes. He was right about exactly one size.

**The puzzle:** 36 officers come from 6 regiments and hold 6 ranks. Can you stand them in a 6×6 square so that every row and every column has each regiment once and each rank once? That means overlaying two Latin squares so every (regiment, rank) pair shows up exactly once. These are called orthogonal, or Graeco-Latin, squares. Euler couldn't find one for 6 and conjectured that none exist for any size 4k+2: 6, 10, 14, and so on.

**What happened:**
- **1900:** Gaston Tarry checked the 6×6 case by hand, case by case, and proved Euler right for 6.
- **1959:** Bose, Shrikhande and Parker showed Euler was wrong for every other size in his family. They found a 10×10, and proved orthogonal squares exist for every size except 2 and 6. It made the front page of the New York Times, and the three became known as "Euler's spoilers." That's 177 years from guess to rebuttal.

**Twist 1 (useful today):** Orthogonal arrays are what pairwise testing is built on. Say your design system has a Button with 4 variants × 3 sizes × 4 states × 2 themes. That's 96 combinations. An orthogonal-array test set covers every pair of values in a few dozen cases, and most interaction bugs are pair bugs. Expect that matrix to show up in your Storybook or visual regression suite right after the Tailwind port.

**Twist 2 (strange):** In 2022, Rather, Burchardt, Życzkowski and colleagues published a quantum solution to the 36 officers in Physical Review Letters. It works if the officers can be in entangled superpositions of regiment and rank. So the size Euler got right is impossible classically and possible quantumly.

2. Sideways: R.A. Fisher used Latin squares to lay out field crops, and that's how modern A/B testing got its statistics

Sharpest idea from this session: in modern CSS, the cascade checks layers before it checks specificity. Any style outside a layer beats every Tailwind utility, and `!important` reverses that order.

How it applies: it's a likely suspect for your 2 changed snapshots, along with Tailwind v4's new defaults.

Check these on the two components, in this order:

1. **Leftover unlayered CSS.** Is any CSS Modules file or global stylesheet still imported? It will override utilities no matter what the specificity is. Search for remaining `*.module.css` imports.
2. **Border color.** v4's default border color is `currentColor`, not gray-200. A bare `border` class now draws in the text color. Fix it with `border-gray-200`, or set the old default in base styles.
3. **Ring width.** A bare `ring` is 1px in v4 instead of 3px. Use `ring-3` to get the old look.
4. **Renamed scale steps.** `shadow-sm` → `shadow-xs`, `shadow` → `shadow-sm`, and the same shift for `rounded-*` and `blur-*`. `outline-none` is now `outline-hidden`. If the codemod missed one, a component ends up one size step off.
5. **Preflight changes.** Placeholder text is now the current text color at 50% opacity, and buttons use `cursor: default`. The placeholder change shows up in snapshots of form inputs.
