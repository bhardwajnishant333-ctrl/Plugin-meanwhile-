**Meanwhile:**
**After this migration, your app gets compiled by two different toolchains, and neither one checks your types.**

In dev, Vite barely bundles. It serves your source files to the browser as native ES modules and transforms each file on request with esbuild. Your node_modules are pre-bundled once, also with esbuild. `vite build` is a different pipeline: Rollup bundles everything, with its own CommonJS plugin. (Newer Vite versions are moving to Rolldown to bring dev and build closer together. Which one you get depends on your version, so check it.)

That split is where "works in dev, breaks in build" comes from:
- **CommonJS interop.** A `default` import from an old CJS package can resolve to the module in one pipeline and to `{ default: module }` in the other.
- **One file at a time.** esbuild compiles files in isolation, so `const enum` used across files, and re-exported types without `export type`, can break. That's why Vite wants `isolatedModules: true` in tsconfig.
- **Env vars.** `process.env.X` becomes `import.meta.env.VITE_X`, and only variables with the `VITE_` prefix reach the client.

**The twist that matters right now:** esbuild strips TypeScript types and never checks them. If your webpack setup used `ts-loader` or `fork-ts-checker-webpack-plugin`, type errors used to fail the build. Unless something replaces that check, a type error now ships silently, and your tests can still pass. The official react-ts template guards against this with `"build": "tsc -b && vite build"`. When the agent finishes, check two things: that `package.json` (or CI) runs `tsc` somewhere, and that you ran `vite build && vite preview` at least once, not just the dev server.
