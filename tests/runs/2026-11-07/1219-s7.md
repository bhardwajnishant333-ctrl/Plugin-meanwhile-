**On Redis, Celery can quietly run the same task twice. With invoice exports, that means the same invoice goes out twice.**

Here's how. When the broker is Redis (SQS works the same way), a message the worker hasn't acknowledged isn't really "taken". It's hidden for `visibility_timeout`, which defaults to 1 hour. If nothing acknowledges it in that time, Redis puts it back in the queue and another worker picks it up. Two common setups run into this:

- **`acks_late=True`** acknowledges a task only after it finishes. People turn it on so a crashed worker doesn't lose work. But any task that runs longer than an hour gets handed out again while the first run is still going.
- **ETA or countdown tasks** (`apply_async(countdown=...)`, retries with a long backoff) sit unacknowledged in the worker until their start time. If that's more than an hour away, the task gets redelivered, and Celery's docs warn about exactly this.

By default Celery acknowledges a task when the worker receives it, before it runs, so normal tasks don't hit this. The catch is that a worker crash mid-task then loses that task without a trace.

**The twist:** you get to choose between possibly losing a task and possibly running it twice. "Exactly once" isn't one of the options. So the safe design is a task that can run twice without harm. For example, give each export a unique key (such as invoice ID plus period), record it in the same database transaction as the export, and skip any run whose key is already recorded. Separately, queue the task with `transaction.on_commit`. Otherwise a worker can start before the invoice row has been saved.

I can't see your config, so this is a general Celery behaviour, not a bug I've found in your code. Two things worth checking in the agent's diff: whether it sets `acks_late` or long countdowns, and whether a second run of a task would create a second invoice.

**Meanwhile:**

**On Redis, the one-hour countdown starts when a worker grabs a task, not when the task starts running.**

How it works, in the Celery/kombu Redis setup:

- When a worker takes a message off the queue, kombu also writes a copy to an `unacked` hash and records the time in an `unacked_index` sorted set. Once the task is acknowledged, both entries are deleted.
- Workers regularly sweep that sorted set, using a lock so two don't sweep at once. Any entry older than `visibility_timeout` gets pushed back onto its queue. Nothing checks whether a worker is still busy with it. Redis can't tell "running for a long time" apart from "worker died".
- You change the timeout with `broker_transport_options = {"visibility_timeout": 43200}` (12 hours). The sweep is done by the workers themselves, so as far as I know each worker uses its own setting. Every worker and every producer should have the same value. Otherwise one with a short timeout can put back tasks that others are still working on. I'm confident about the general mechanism. The exact key names and how often the sweep runs can differ between kombu versions.

**The twist: prefetching.** By default a worker grabs 4 messages per process at a time (`worker_prefetch_multiplier=4`). Grabbed messages count as unacknowledged, so their hour is running even while they wait in the worker's buffer. Picture a 2-second invoice export waiting behind a 70-minute report. It gets handed out again before it has even started. That's why Celery's docs recommend pairing `acks_late=True` with `worker_prefetch_multiplier=1` for long tasks.

A longer timeout isn't free either. It's also how long a task held by a crashed worker stays stuck before it comes back. Set it a bit longer than your slowest task plus your longest countdown, and no longer. Then make tasks safe to run twice, so occasional duplicates don't hurt.

Quick things to check in the agent's diff: `acks_late`, the prefetch setting, any countdown or ETA longer than an hour, and whether `visibility_timeout` is set the same everywhere.

**Meanwhile:**

That failure is expected with this setup, and the view is probably fine.

**Why `delay` is called 0 times:** a plain `@pytest.mark.django_db` runs each test inside a database transaction and rolls it back at the end. Nothing is ever committed, so Django never runs the `transaction.on_commit` callbacks and `export_invoice.delay` is never reached.

**Fix (recommended):** pytest-django (4.4 and later) has a `django_capture_on_commit_callbacks` fixture that collects those callbacks and runs them for you:

```python
@pytest.mark.django_db
def test_export_invoices_enqueues_on_commit(client, django_capture_on_commit_callbacks, mocker):
    mock_delay = mocker.patch("exports.tasks.export_invoice.delay")  # or your existing patch
    invoice = ...  # existing setup

    with django_capture_on_commit_callbacks(execute=True) as callbacks:
        client.post(...)  # the request that triggers the export

    assert len(callbacks) == 1
    mock_delay.assert_called_once_with(invoice.pk)
```

`execute=True` runs the callbacks when the `with` block ends, and `callbacks` lets you also check that exactly one was registered. If you use Django's `TestCase` style, the same thing is `self.captureOnCommitCallbacks(execute=True)` (Django 3.2+).

**Alternative:** `@pytest.mark.django_db(transaction=True)` makes the commits real, so the callbacks run. It's slower, though, because it empties the tables after every test. That adds up in a suite that already takes 30 minutes.

**Two other things to check:**
- If the fix still shows 0 calls, look at what you're patching. It has to be the same `export_invoice` object the view uses. Patching `.delay` on the task object, as above, works whether the view imports the module or the function.
- Don't change the view to call `delay` directly just to make the test pass. Queueing after the commit is the correct behaviour, because a worker that starts earlier can look for an invoice row that hasn't been saved yet.
