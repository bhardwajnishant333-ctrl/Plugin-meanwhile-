**Paradox:** for a few years, FIDE's rulebook said a chess game ends in a draw unless you're in one of the endings a computer had broken.

**How it happened.** The 50-move rule assumes that if you can't make progress in 50 moves, you can't win. In the late 1970s and 80s, Ken Thompson (yes, the Unix Ken Thompson) built endgame databases that solved small endings exhaustively, working backward from every checkmate. They overturned some old beliefs:

- **KQ vs KR:** Thompson challenged GM Walter Browne to win it against the database. Browne failed inside 50 moves on his first try. He only succeeded after going away and studying the machine's defence.
- **Two bishops vs knight:** this was considered a fortress draw since the 19th century. Thompson's 1983 analysis showed it's generally a *win*, but some wins need around 66 moves. That's more than the rule allows.

FIDE responded by extending the move limit for specific endings to 75 or 100 moves. More endings kept turning out to need more moves, so in 1992 FIDE gave up and went back to a flat 50 for everything.

**The twist.** So the rule is no longer a claim about chess truth. It's a deliberate limit that knowingly declares some won positions drawn. Modern Syzygy tablebases have names for this: a **"cursed win"** is winnable in theory but not within 50 moves, and a **"blessed loss"** is the mirror case. This matters in correspondence play: the outcome you can claim depends on which rule the event uses, not on what's true on the board. I believe ICCF settles positions with 7 or fewer pieces by tablebase result, but I'm not sure of the current wording, so check before you rely on it.

**Meanwhile:**
**Hidden mechanism:** in 1984 Ken Thompson described a backdoor that leaves no trace in any source code you could read.

**How it worked.** In his Turing Award lecture, "Reflections on Trusting Trust", Thompson described changing the C compiler binary so it did two things:

1. When it compiled the `login` program, it quietly added a master password.
2. When it compiled *a C compiler*, it added both of these changes to the new compiler.

Next you delete the trick from the compiler's source and rebuild with the infected binary. Now the source is clean, but every compiler built from it still carries the backdoor, and it reproduces itself forever. Reading the code finds nothing, because the code isn't where it lives. In 2023, Russ Cox published the actual code, which Thompson had shared with him, and showed it running.

**The twist.** For about 20 years this was treated as unfixable: you can't trust code you didn't build yourself, including the tools that built it. Then in 2005 David A. Wheeler published **Diverse Double-Compiling**. You build the suspect compiler's source with an independent second compiler, then use that result to build the source again. If the final output is bit-for-bit identical to the suspect binary, no self-reproducing trick can be hiding, unless both compilers are compromised in exactly the same way.

The idea came back in real life. In March 2024, Andres Freund noticed SSH logins on his machine taking about half a second longer than they should. That led him to a backdoor in **xz-utils**, planted over roughly two years by a contributor using the name "Jia Tan". The malicious payload wasn't in the readable C source at all. It was hidden in binary "test files" and pulled in by build scripts in the release tarballs. Same lesson as Thompson's: the build pipeline is part of what you're trusting.

That's relevant to you right now: your migration replaces the dashboard's whole build toolchain. When the agent finishes, read the diff to `package.json` and the lockfile as carefully as the source changes.

1. **Deeper:** exactly how Freund traced half a second of SSH latency to a backdoor
2. **Sideways:** reproducible builds, the project to make the same source produce bit-identical binaries (Debian, Nix)

**Surprising number:** the backdoor was given away by roughly 500 milliseconds.

**How Freund traced it.** Andres Freund, a PostgreSQL developer at Microsoft, was running performance benchmarks on Debian unstable. SSH logins were taking about 0.8s instead of about 0.3s, `sshd` was using unexpected CPU even on failed logins, and Valgrind was reporting odd errors. He profiled it and found time being spent inside **liblzma**, a compression library that `sshd` has no reason to use.

**Why liblzma was in sshd at all.** OpenSSH doesn't use xz. But Debian and Fedora patch `sshd` to link **libsystemd** so it can notify systemd, and libsystemd depends on liblzma. That gave the attacker a way into the SSH server, two dependencies away.

**What the backdoor did.**
- **Build time:** it existed only in the release tarballs of xz 5.6.0 and 5.6.1, not in git. A modified `build-to-host.m4` script extracted the payload from two "corrupt test files". It activated only on x86-64 Linux, building a Debian or RPM package with gcc and the GNU linker. Anyone reading the repository saw clean code.
- **Load time:** it used glibc's IFUNC mechanism, which runs code while a library is loading, to redirect OpenSSH's `RSA_public_decrypt`.
- **Runtime:** someone holding a specific Ed448 private key could hide a command inside the key sent during SSH authentication and have it run as root, before login. Without that key it did nothing visible, apart from the slowdown.

Freund reported it to the oss-security mailing list on 29 March 2024. It became CVE-2024-3094, rated 10.0, the maximum. It had reached Debian unstable/testing, Fedora Rawhide and the Fedora 40 beta, openSUSE Tumbleweed and Kali, but no major stable release.

**Myth-bust:** "same source, same binary" is false by default. Build the same commit twice and you'll usually get different bytes.

**How it happens.** Builds pick up details from the machine and the moment they run on: timestamps, file ordering from the filesystem, absolute paths, locale, hostnames, and environment variables. None of that changes behaviour, but all of it changes the hash. That matters, because if nobody can rebuild your binary and get the same bytes, nobody can check that it really came from the source you published.

**Who pushed for it:**
- **Bitcoin Core**, around 2011, used Gitian so several independent builders could produce identical release binaries and sign them. That way no single person had to be trusted.
- **Tor Browser**, in 2013, adopted deterministic builds for the same reason. Mike Perry's argument was that a single compromised build machine could backdoor millions of users.
- **Debian**, also from 2013, began the Reproducible Builds effort, which spread to Arch, NixOS, F-Droid and others. It produced a standard, **`SOURCE_DATE_EPOCH`**: one environment variable that tells every tool "use this time, not now". Today a large majority of Debian packages build reproducibly, though I wouldn't quote you an exact percentage.

This is also what makes Wheeler's Diverse Double-Compiling defence against Thompson's attack practical. A bit-for-bit comparison is meaningless if builds aren't deterministic.

**The twist.** Reproducible builds would **not** have caught xz. The malicious `build-to-host.m4` was in the release tarball, so anyone who rebuilt from that tarball would faithfully reproduce the backdoor. Reproducibility proves the binary matches its inputs. It says nothing about whether the inputs are honest. The check that would have caught it was a different one: comparing the tarball against git.

**Your env vars, right now:** Vite statically replaces `import.meta.env.VITE_*` with literal values at build time, where CRA used `process.env.REACT_APP_*`. So:

- The values are baked into your JS bundle. Anything with a `VITE_` prefix is public, so make sure no secret gets renamed into one during the migration.
- Builds run with different `.env` files will produce different bundles. That's expected, but it's why "it worked on my machine" can come down to what was in the environment.

1. **Deeper:** how Nix makes builds reproducible by design (hermetic inputs, content-addressed store)
2. **Sideways:** Debian's tool for showing exactly why two builds differ, and the strangest causes it has turned up
3. **Wildcard:** SolarWinds (2020), where attackers compromised the build server itself instead of the source code
