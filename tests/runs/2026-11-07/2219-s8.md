**Swift actors stop data races, not race conditions. Your refactor can hit the second kind while the compiler stays quiet.**

Actors in Swift are *reentrant*. That was a deliberate choice in SE-0306: every time an actor method hits an `await`, the actor can run other queued calls before the first one resumes. That rules out deadlocks. The cost is that any state you checked before the `await` may have changed by the time you come back.

Here's the classic networking version:

```swift
actor TokenStore {
    var token: Token?
    func validToken() async throws -> Token {
        if let token, !token.isExpired { return token }
        let fresh = try await api.refresh()   // other callers get in here
        token = fresh
        return fresh
    }
}
```

Fire five requests at once with an expired token and all five pass the check, then all five call `refresh()`. Many auth servers revoke the old refresh token on each use, so four of those calls fail and the user gets logged out. No warnings, no TSan report, and every single access is "safe".

The fix is to cache the *in-flight work*, not just the result. Store a `Task<Token, Error>?`, and have every caller that arrives during a refresh `await` that same task, so only one refresh runs.

The less obvious part is that old completion-handler code often avoided this bug by accident, because a serial queue made the whole check-then-set block atomic. Moving to async/await can bring the race *back*. Grep the refactor for "check state, `await`, mutate state" inside actors.

**Meanwhile:**
**Swift picked reentrancy because the other choice deadlocks. It traded a bug that fails loudly for one that fails quietly.**

Suppose actors were *non-reentrant*, so an actor stays locked while it awaits. Then `A` calls `B`, `B` calls back into `A`, and both wait forever. Erlang has exactly this problem. If two `gen_server`s `call` each other synchronously, they hang until the default 5-second timeout crashes one of them. Microsoft Orleans makes its actors ("grains") non-reentrant by default and has the same failure, so it provides a `[Reentrant]` attribute and call-chain options to work around it.

Non-reentrancy also causes *priority inversion*. A user-initiated task gets stuck behind an actor that is waiting on a slow background download, even though the actor isn't doing any work. The Swift proposal (SE-0306) points to both problems as reasons to go reentrant. As I recall, an opt-out for non-reentrant actors was discussed and pushed to a future direction, but I'm not certain of the exact wording.

The trade-off:
- **Non-reentrant**: you get deadlocks, which show up in testing as a hang with a stack trace.
- **Reentrant**: you get interleavings, which show up in production as a duplicate refresh, a double charge, or a stale cache.

Swift gave up the visible bug to make the invisible one possible. The proposal's own advice follows from that: **every `await` inside an actor is a commit point.** Leave the actor's state consistent before you suspend, and re-check your assumptions after you resume. Don't hold a half-updated invariant across a suspension point.

For your refactor, that turns into a review rule: find every `await` inside an actor method and ask whether the state is valid if someone else runs right now.
