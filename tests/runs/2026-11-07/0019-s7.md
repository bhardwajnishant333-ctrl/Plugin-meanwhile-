**Meanwhile:**
When your embassy firmware has nothing to do, it isn't running a scheduler loop. The core is asleep on a single `WFE` instruction, and only an interrupt wakes it.

**How it works:** Every `async fn` your driver uses is compiled into an enum, a state machine with one variant for each `.await` point. Each variant stores only the locals that stay alive across that await. `#[embassy_executor::task]` puts that enum in a `static` whose size the compiler fixes at build time. There's no heap and no per-task stack. When you call `i2c.read(...).await`, the HAL starts the transfer and saves a waker. The task returns `Pending`. If no other task is ready, the executor runs `WFE` and the core stops. When the I2C/DMA interrupt fires, its handler calls the waker. That marks the task ready and sends an event (`SEV`), so the core wakes, polls that one task, and goes back to sleep. Timers use the same mechanism through a hardware alarm. With the low-power feature, embassy-stm32 can drop into STOP mode between events, but I'm not sure exactly how it handles each chip family.

**The catch:** In a C RTOS you guess each thread's stack size and hope it's enough. Here the compiler calculates the memory each task holds, but only for what lives across an `.await`. So a local `[u8; 512]` buffer that you `.await` while holding becomes permanent static RAM for that task, sitting in `.bss` the whole time, even between reads. Move the `.await` above the buffer, or limit the buffer's scope, and that RAM goes back to the shared stack. Where you put an `.await` changes your memory map. The C version never had that problem. Check `cargo size` before and after the port.

**User:** ugh it stopped: `error[E0277]: RefCell<Option<I2c<'static, Async>>> cannot be shared between threads safely` at `static BUS: RefCell<Option<I2c<'static, Async>>> = RefCell::new(None);` (help: `Sync` not implemented). it's shared between the sensor task and a calibration task

**Meanwhile:**
Rust rejects this because a `static` can be reached from any context at once, so its type must be `Sync`. `RefCell` is not `Sync`. Even if it compiled, it would be the wrong tool here: both tasks keep the bus busy across `.await` during a transfer, so they need an **async mutex**. A blocking mutex or a `RefCell` isn't enough.

Here's the usual embassy fix: put the bus in an `embassy_sync` `Mutex` and give both tasks a `&'static` to it.

```rust
use embassy_sync::{blocking_mutex::raw::CriticalSectionRawMutex, mutex::Mutex};
use static_cell::StaticCell;

type Bus = Mutex<CriticalSectionRawMutex, I2c<'static, Async>>;
static BUS: StaticCell<Bus> = StaticCell::new();

// in main
let i2c = I2c::new(/* your existing init */);
let bus: &'static Bus = BUS.init(Mutex::new(i2c));
// spawn both tasks with `bus`, using whatever spawn form your
// embassy-executor version already uses in this project

#[embassy_executor::task]
async fn sensor_task(bus: &'static Bus) {
    loop {
        let mut buf = [0u8; 6];
        {
            let mut i2c = bus.lock().await;
            let _ = i2c.write_read(ADDR, &[REG], &mut buf).await;
        } // guard drops here: release the bus before sleeping
        Timer::after_millis(100).await;
    }
}
```

`calibration_task` follows the same pattern: `bus.lock().await` around its transactions.

Notes:
- **Keep the lock scope tight.** If you hold the guard across `Timer::after`, the calibration task can't use the bus during that wait.
- **`CriticalSectionRawMutex` is safe in every context.** `ThreadModeRawMutex` is slightly cheaper, but use it only if both tasks run on the normal thread-mode executor and not on an `InterruptExecutor`.
- **If the driver is generic over `embedded_hal_async::i2c::I2c`**, the cleaner option is `embassy_embedded_hal::shared_bus::asynch::i2c::I2cDevice::new(bus)`. Each task gets its own handle that implements the I2C trait and locks for every transaction. The driver code doesn't change.
- **Dependencies:** this needs `embassy-sync` and `static_cell` in `Cargo.toml`. Embassy projects usually have both already.

The idea worth keeping: an async lock held across an `.await` is the async version of holding a thread's stack. Whatever you keep across the suspension point blocks other tasks or takes memory until you let go.
