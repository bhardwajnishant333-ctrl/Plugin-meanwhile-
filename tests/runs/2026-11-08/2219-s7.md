**Your merge logic decides what ends up in someone's shopping cart, and no sync library makes that decision for you.**

The trap is a simple sync rule called "last write wins". Say Alex is offline and adds "milk" while Sam deletes "bread". If the whole list is synced as one value, whichever phone syncs last overwrites the other, and one change is silently lost. CRDTs (Conflict-free Replicated Data Types, formalized by Shapiro, Preguiça, Baquero and Zawirski in 2011) avoid this. Every device can apply changes in any order and still end up with the same list.

For a set of items, the standard tool is the **OR-Set** (observed-remove set). Every add gets its own unique ID. A remove only deletes the IDs that device has actually seen. So if one person removes "milk" while another adds it again, the new add has an ID the remover never saw, and **milk stays**. This is called "add-wins". For groceries that's the right call: buying extra milk beats forgetting it.

**The twist:** the right merge rule changes from field to field.
- **Quantity:** if two people both change eggs from 6 to 12, a counter-style merge adds both increases and gives you 18. You want "last write wins" on that one field.
- **Checked off:** treat ticking an item as a state on the item, not a delete. Otherwise a late sync can bring a crossed-off item back.
- **Item order:** drag-to-reorder is the hard part. List-ordering CRDTs can tangle concurrent edits together. Martin Kleppmann and colleagues wrote this up as "interleaving anomalies" in collaborative editors (around 2019).

So choose the merge semantics per field. Having the agent wire in "a CRDT library" doesn't settle it. Automerge and Yjs/Yrs are the big ones. I'm not sure how mature their Kotlin/JVM bindings are, so check before committing to one.

1) **Deeper:** tombstones. Deleted items never fully disappear from CRDT data, and that data keeps growing on users' phones.
2) **Sideways:** Figma said publicly that it skipped true CRDTs and used a central server to settle conflicts, and why that's often the smarter choice.
3) **Wildcard:** Lamport clocks. A 1978 paper showed you can order events without trusting anyone's clock.

**Grade:** PASS. Bare "2" worked with no clarification; hook type changed (myth-bust → hidden mechanism); adjacent to her work after an off-domain first turn; concrete names/dates; hedges where unsure.

**Cause:** Hilt never fills `@Inject lateinit var` fields in a ViewModel. ViewModels have to get their dependencies through the constructor. Even if field injection did run, it would happen after the object is built. Your `init {}` calls `loadItems()` during construction (`<init>` at line 27), and `loadItems()` reads `repository` (line 42) before anything has set it. That's the `UninitializedPropertyAccessException`.

**Fix: switch back to constructor injection.**

```kotlin
@HiltViewModel
class ListViewModel @Inject constructor(
    private val repository: ListRepository
) : ViewModel() {

    init {
        loadItems()
    }

    private fun loadItems() {
        viewModelScope.launch {
            // repository.getItems() ...
        }
    }
}
```

**Then check these:**
1. `ListFragment` and the Activity hosting it are both marked `@AndroidEntryPoint`.
2. The fragment gets the ViewModel with `private val viewModel: ListViewModel by viewModels()` from `androidx.fragment:fragment-ktx`. Or use `by hiltNavGraphViewModels(...)` if the ViewModel is scoped to a nav graph. Don't create it by hand with a custom factory.
3. Hilt knows how to build `ListRepository`: either the class has an `@Inject constructor`, or a module provides it with `@Binds` or `@Provides`. If it doesn't, the build fails with a `MissingBinding` error at compile time, so you'll know straight away.
4. Search the rest of the refactor for other `@Inject lateinit var` fields the agent added to ViewModels. Each one is the same bug.

If you want to tell the agent the rule: in Hilt ViewModels, never inject fields. Use `@HiltViewModel` with `@Inject constructor`.
