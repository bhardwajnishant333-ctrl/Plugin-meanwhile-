**The biggest jump in modern chess engine strength came from shogi, the Japanese chess variant, and it works the way a good render loop does: recompute only what changed.**

In 2018 Yu Nasu designed NNUE ("efficiently updatable neural network") for shogi engines. The trick: the input to the network is a huge sparse vector of piece-on-square features, and a single move flips only a handful of them. So the engine doesn't redo the expensive first layer for every position it looks at. It adds and subtracts the few columns that changed in a stored result. That makes neural evaluation cheap enough to run at alpha-beta search speed, millions of positions per second on an ordinary CPU, with no GPU. Stockfish adopted it in 2020 (Stockfish 12) and gained roughly 80–100 Elo almost overnight. Before that, the common belief was that strong neural evaluation needed AlphaZero-style hardware.

The twist: the win came from a data-structure idea, not a smarter evaluation. Stockfish 12 shipped a deliberately small network because cheap incremental updates beat a bigger network that has to recompute everything. It's the same trade you make when a dashboard updates aggregates from deltas instead of re-reducing the whole dataset on every filter change.

**A bug in Deep Blue may have rattled Kasparov more than anything it calculated, though that story is disputed.**

The 1997 rematch, Game 1. Kasparov won it. But late in the game (the 44th move is the one usually cited, often given as ...Rd1) Deep Blue played a move that looked strangely pointless. In *The Signal and the Noise* (2012), Nate Silver relays an account from IBM's Murray Campbell: a bug left the machine unable to settle on a move, so it fell back to a move with no real reasoning behind it. The story goes that Kasparov read it as depth he couldn't see, a machine judging the position at a level beyond him.

Afterwards he suggested humans might have helped the machine. Deep Blue won the match 3.5–2.5. Whether the bug actually shook him is contested, and Campbell's own later accounts are more cautious than the popular version, so treat the cause and effect as a good story, not a proven fact.

The twist: if you can't see a system's reasons, you tend to supply intent yourself, and you lean toward giving it credit. Kasparov did that with a fallback move. It's the same habit you need to watch for when an agent's diff, or a test that suddenly passes, looks cleverer than you can explain.

**A Playwright screenshot baseline captures your fonts, your GPU and your OS as much as your UI.**

Playwright already expects this. By default it puts the browser and platform in the baseline's file name, for example `dashboard-chromium-darwin.png` versus `dashboard-chromium-linux.png`. Its docs say outright that rendering varies with OS, version, hardware and headless mode. The usual causes:
- **Text:** macOS draws text with its own rasteriser, while Linux usually uses FreeType with different hinting and anti-aliasing. The same font at the same size comes out a few pixels different at the edges of each letter.
- **GPU:** CI machines often have no GPU, so Chromium falls back to software rendering. That changes how canvas and SVG chart edges are anti-aliased, which matters a lot on a dashboard full of charts.
- **Data:** time zone and locale change axis labels and number formatting, so "Nov 8" can come out as "8 Nov", or a chart can be shifted by a day.

The fix is to pin everything except your UI:
- Generate and check baselines in the same environment, typically the official Playwright Docker image matched to your installed Playwright version.
- Set `timezoneId` and `locale` in the config.
- Use `mask` over live data like timestamps and changing numbers.
- Leave `animations: 'disabled'` on; it's the default for `toHaveScreenshot`.
- If you have to, add a small `maxDiffPixels` or `threshold`, but raise it only as a last resort, because a loose threshold also hides real regressions.

The twist: a flaky visual test usually isn't flaky. It's an exact test of an environment you didn't mean to test. The same goes for agent-written code that "works on my machine": decide what you're actually asserting before you trust a green run.
