**"Always store datetimes in UTC" is the wrong rule for future appointments.**

UTC is right for things that already happened, like a payment or a log line. A future appointment is different: it's a promise about a local clock time, "9:00 in Cairo," and governments change their clock rules with very little notice. In 2016 Egypt cancelled daylight saving days before it was due to start. I'm going from memory here, but I think the notice was about three days. In late 2022 Mexico ended DST for most of the country weeks before the clocks would have changed.

Here's what goes wrong. With Django's `USE_TZ=True`, a 9:00 summer booking is turned into a UTC instant when it's saved, using the tz rules your server has that day. If the rules then change and your tzdata updates, the same UTC instant now shows as 8:00. The patient arrives at 9:00 as booked, but your system has them down for 8:00. Your test suite won't catch this, because the tests run with a single version of tzdata.

The fix many calendar systems use: store the local wall time plus the IANA zone name (`"Africa/Cairo"`), and convert to UTC when you read it. If you need fast queries, keep a cached UTC column and recompute it whenever tzdata changes.

The twist: UTC records an exact instant. Your clinic is promising a time on the patient's local clock, and that's what the database should store.

**Hubble's Deep Field camera had pixels too big for the detail it was trying to record, and the fix was to deliberately point it slightly off between exposures.**

In December 1995 Hubble stared at an empty-looking patch of Ursa Major for about 10 days and took 342 exposures through four filters. The resulting image showed roughly 3,000 galaxies. The problem was the WFPC2 wide-field chips: each pixel covered about 0.1 arcsec, which was coarser than the detail Hubble's optics could deliver. Fine structure got averaged inside single pixels and lost.

The team moved the telescope by fractions of a pixel between exposures (dithering). Andrew Fruchter and Richard Hook then wrote the algorithm that combined them. Its formal name is "variable-pixel linear reconstruction," and everyone calls it drizzle. It shrinks each input pixel into a smaller "drop" (the `pixfrac` setting), drops it onto a finer output grid, and weights each output pixel by how much the drops overlap it. Because every sub is offset differently, together they sample the sky at points no single pixel ever covered. The published paper came out in PASP in 2002, years after the method was in use.

The twist for your rig: drizzle only gets back detail that your sampling lost. Image scale = 206.265 × pixel size (µm) / focal length (mm). As an example, a 72 mm refractor at about 430 mm with 3.76 µm pixels gives about 1.8"/px. Under 2-3" seeing that's around the borderline, so drizzle may help on your best nights. If your scale is already small compared with your seeing, drizzle adds no real detail. It just spreads your signal across more pixels and makes the image noisier. It also needs dithering between subs. Guiding drift dithers a little by accident, but random dithers set in your capture software work much better.

The bigger idea: many slightly misaligned, coarse measurements can beat one precise one, provided the misalignment varies and you know how much each frame moved.

**Cause:** `request.user.patient` is a reverse one-to-one lookup from `User` to `Patient`. It raises `RelatedObjectDoesNotExist` when that user has no `Patient` row. Your `setUp` creates a bare `User` with `create_user("p1", password="x")` and nothing creates a `Patient` for them. `force_authenticate` works, but the serializer fails at line 41.

**Fix the test** by creating the profile in `setUp`:

```python
def setUp(self):
    self.user = User.objects.create_user("p1", password="x")
    self.patient = Patient.objects.create(user=self.user)  # add any required fields
    self.client.force_authenticate(user=self.user)
```

**If this test used to pass,** something probably created the `Patient` automatically before, most likely a `post_save` signal on `User`. Check these:
- Was the signal removed, renamed, or moved recently? `git log -p -- bookings/signals.py` will show it.
- Is it still connected? Signals usually only register if `bookings/apps.py` imports them in `ready()`, and `INSTALLED_APPS` references that AppConfig.
- Did a factory or fixture that used to make the patient get replaced by plain `create_user`?

If the signal is supposed to exist, fix the wiring rather than patching the test. Otherwise every test that builds a user will need the same fix.

**Also harden the endpoint:** an authenticated user with no patient profile currently gets a 500. Return a 403 instead:

```python
# permissions.py
from rest_framework.permissions import BasePermission

class HasPatientProfile(BasePermission):
    message = "A patient profile is required to book."
    def has_permission(self, request, view):
        return hasattr(request.user, "patient")
```

Add it to the view's `permission_classes`. `hasattr` works here because `RelatedObjectDoesNotExist` is a subclass of `AttributeError`, so it returns `False` instead of raising. Then add a test showing a user without a patient gets a 403.
