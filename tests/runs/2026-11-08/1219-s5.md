**Meanwhile:**
**Your motor controller and a telescope mount both fight a disturbance that repeats at the same angle on every turn. Astronomers learned to cancel it by playback decades ago.**

**Your side: cogging torque.** In a permanent-magnet motor, the rotor magnets are drawn toward the stator's iron teeth even with zero current. This shows up as a torque ripple that repeats at fixed rotor angles. The number of ripple cycles per mechanical revolution is the least common multiple of slot count and pole count. That's why fractional-slot designs like 12 slots and 14 poles (LCM 84) are popular: more cycles per turn, each one smaller. On an e-bike you feel it as notchiness at low speed and pull-away. Its key property is that it depends only on rotor position, not on time or load.

**Their side: periodic error.** A telescope mount has to rotate at sidereal rate, about 15 arcseconds per second, to keep a star still. Classic mounts drive the axis through a worm gear, and no worm is perfectly round or perfectly centered. Every turn of the worm (a few minutes on typical amateur mounts) adds the same slow wobble. In a long exposure that wobble stretches stars into short streaks. Newer strain-wave (harmonic drive) mounts such as ZWO's AM5 have their own periodic signature too.

**The shared fix: periodic error correction (PEC).** Amateur mounts have offered it for a long time. You guide on a star for a few worm cycles, record the tracking error against worm angle, and store it in a table. The mount then plays back the inverse of that error as feedforward, keyed to the worm's position. The guide camera's feedback loop only has to clean up what's left.

That maps directly onto FOC. A cogging-compensation lookup table, indexed by mechanical rotor angle and added to the q-axis current command, is the same thing as PEC. Here's the twist: for a disturbance that is purely position-locked, feedback is the wrong main tool. A PI loop can only push back after the error has already happened, and the error gets worse as its bandwidth runs out. A position-indexed feedforward table cancels the ripple before it occurs and costs almost nothing in compute: one table read and one add per control cycle.

The practical catch is that the table is only as good as your angle reference. Astronomers learned this through "PEC drift": if the worm's index sensor slips, the playback falls out of phase and makes tracking worse. The motor version is encoder offset error or a loss of absolute position after power-up.

**Meanwhile:**
**A single delay line in a feedback loop gives you, in theory, infinite gain at every harmonic of one frequency at once.**

**The principle.** The internal model principle (Francis and Wonham, 1976) says that to reject a disturbance perfectly, the controller has to contain a model of whatever generates that disturbance. A constant disturbance is generated by an integrator, which is why integral action removes steady-state error. A periodic disturbance with period T is generated by a delay of length T fed back on itself: 1 / (1 − e^(−sT)). That transfer function has poles at every multiple of 1/T, so it has infinite gain at the fundamental and at all of its harmonics. One block covers the whole periodic signal, whatever its waveform.

**Where it came from.** Inoue and colleagues named it "repetitive control" around 1981, working on power supplies for proton synchrotron magnets. Those supplies had to follow the same current waveform on every accelerator cycle with very high accuracy. It later became standard for repeatable runout in hard disk drive track following, where the same off-center wobble returns on every platter revolution.

**In discrete form it's a learning table.** Your PEC/cogging table stops being something you measure once and becomes something that updates itself on every pass:

`table[θ] += k · error[θ]`

Each revolution, the error at each angle nudges the correction stored for that angle. Repeating error shrinks pass by pass, and the table converges to the inverse of the cogging profile without a bench calibration.

**The catches, which are the real lesson:**
- **Index by angle, not time.** A textbook repetitive controller uses a time delay. Your period changes every time the rider speeds up, so the buffer has to be indexed by mechanical angle (spatial-domain repetitive control). This is also where the encoder-offset problem from last time comes back.
- **You can't have infinite gain everywhere.** Harmonics go all the way up, but your plant model doesn't stay accurate that high, and phase errors there can destabilize the loop. Real implementations put a low-pass filter Q inside the loop, giving up the highest harmonics to stay stable.
- **The waterbed effect.** Bode's sensitivity integral says that suppressing error at the harmonics amplifies it somewhere else, between the harmonics. Road bumps, pedal-torque spikes and other non-repeating disturbances can get slightly worse.
- **Freeze it during fast transients.** If speed or load changes faster than the table can track, it learns nonsense. A common guard is to update only above a minimum speed and while the acceleration is small.

**The twist:** the gain is huge, but none of it is applied as feedback at the moment the error happens. Repetitive control uses the previous turn's error as feedforward for the next turn. It's memory standing in for bandwidth, which suits a microcontroller: one RAM array, one multiply-add per cycle, and no faster loop needed.

1) **Deeper:** iterative learning control, the sibling method for tasks that restart from the same state (robot arms, or an e-bike's launch from a standstill)
2) **Sideways:** how hard drives hold a read head to within nanometers on a spinning platter

**A controller that learns between attempts can use the future, because by then the whole previous attempt is already recorded.**

**What ILC is.** Repetitive control assumes one continuous periodic signal. Iterative learning control (ILC) assumes a task with a fixed length that restarts from the same state every time: a robot arm doing the same pick, a printer head doing the same sweep, a motor doing the same startup. Arimoto, Kawamura and Miyazaki wrote the founding paper in 1984, "Bettering Operation of Robots by Learning." After each trial j you have the full error record e_j, and you update the next trial's feedforward:

`u_{j+1}(t) = u_j(t) + L · e_j(t + d)`

**The `+ d` is the key trick.** A real feedback loop is causal: it can only react to errors that have already happened, so plant delay and phase lag limit it. ILC runs between trials, with the whole previous trial stored in memory, so the correction for time t can use error measured at t + d. Choose d to match the plant's delay (its relative degree) and the learning signal lines up with its effect, which no causal controller can do. The same reasoning lets you run zero-phase filtering on the stored trial, forward and then backward (like `filtfilt`), and remove noise with no phase lag.

**The trap that catches people: transient growth.** The textbook convergence condition only guarantees that the error eventually goes to zero. Longman and others showed that ILC laws meeting that condition can see the error grow by orders of magnitude over many trials before it converges, often enough to wreck hardware first. If you want the error to shrink on every trial, you need a stricter, norm-based condition, usually met by adding a low-pass Q-filter that stops learning above some frequency. It's the same trade as in repetitive control: give up the high harmonics to stay safe.

**Where it fits in an e-bike controller.** A real launch from standstill only loosely meets ILC's assumption of identical trials: rider weight, slope and pedal input all change. Look instead at the parts that really do repeat:
- Rotor alignment and the handover from sensorless startup (or Hall sensors) to closed-loop FOC, which runs the same sequence on every power-up
- Bench and production test sequences that run the same motion profile on the same rig

**The twist, aimed at your CI run:** a hardware-in-the-loop test that repeats exactly is the textbook setting for ILC. Every CI run gives you another trial of the same task, so the rig could learn a feedforward correction across runs. A change in the learned correction from one build to the next would then flag that the firmware or the hardware has drifted.

1) **Deeper:** norm-optimal ILC, which picks the update by solving a small optimization each trial instead of hand-tuning L
2) **Sideways:** why industrial robots repeat a position far more precisely than they can reach an arbitrary one
3) **Wildcard:** why the Large Hadron Collider has to account for the Moon's tides
