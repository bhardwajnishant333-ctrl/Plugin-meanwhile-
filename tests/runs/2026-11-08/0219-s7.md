**With the default Redis broker, a Celery retry scheduled more than an hour out can run twice.**

Here's why. When a task calls `self.retry(countdown=...)`, Celery doesn't park the job on a timer. It publishes a new message with an ETA. Any worker can pick that message up right away and then holds it unacknowledged until the ETA arrives. Redis has no real acknowledgements, so Celery imitates them with `visibility_timeout`, which defaults to 3600 seconds. If a message stays unacknowledged longer than that, Redis assumes the worker died and gives the message to another worker. Your second worker then reaches the ETA as well, and the task runs twice. The Celery docs list this under the Redis broker caveats.

The same thing happens with `acks_late=True` and any long task: if a task runs longer than the visibility timeout, it gets sent to a second worker while the first is still working on it.

So in an invoice pipeline, exponential backoff alone is risky. Your 5th or 6th retry can easily wait more than an hour (2^12 seconds is about 68 minutes), and that's when the duplicates start. Duplicates in an invoice pipeline mean double-posted invoices. Two fixes, which work best together: set `visibility_timeout` higher than your longest possible countdown, and make the task idempotent, for example with a unique key per invoice and step, checked before anything has side effects. The idempotency key also protects you when the broker misbehaves in ways nobody predicted.

**The "swing = triplets" rule is wrong on both ends: slow swing is much more lopsided than a triplet, and fast swing is nearly straight.**

In 2002, Anders Friberg and Andreas Sundström measured ride cymbal timing on recordings by top jazz drummers (Music Perception, "Swing ratios and ensemble timing in jazz performance"). At slow tempos the long-short ratio came out at about 3.5:1, far past the 2:1 of a triplet. As tempo went up, the ratio fell roughly in a straight line, until it was close to 1:1 (straight eighths) at very fast tempos, around 300 bpm. The numbers are approximate, but the trend is clear: the short note stays about the same length in milliseconds, and the long note gives up all the time as the tempo rises.

The stranger finding was about the soloists. They played straighter eighths than the drummers, and they landed behind the drummer on the downbeats, yet they lined up with the drummer almost exactly on the offbeats. So the band doesn't lock together on the beat, it locks together on the "and". The laid-back feel comes from the soloist's downbeats sitting behind the drummer's, while that shared offbeat holds everything together.

In other words, what we hear as swing is two players deliberately out of sync on most notes and exactly in sync on one. The fixed point isn't where you'd expect it to be.

Back to your code. The bug is on line 48.

`self.request.retries_override` isn't a Celery attribute, so it comes back as `None`, and `2 ** None` raises the TypeError. The real attribute is `self.request.retries`. It's an int, `0` on the first run, and Celery increments it on each `self.retry()`.

```python
countdown = min(BASE_DELAY * 2 ** self.request.retries, MAX_DELAY)
```

If the agent added `retries_override` on purpose so tests could force a retry count, you probably don't need it. Celery already lets a test set the count:

```python
process_invoice.apply(args=(invoice_id,), retries=5)
```

That sets `request.retries = 5`, so `test_backoff_caps_at_max` can test the real code path. If you want to keep the override anyway, check for `None` explicitly (`x if x is not None else self.request.retries`) rather than `or`, because `or` throws away a legitimate `0`.
