**In 1824 the Royal Navy fixed its corroding copper hulls, and in doing so broke the reason the copper was there.**

**How it worked.** In 1761 the frigate HMS Alarm got a copper skin to keep off shipworm and barnacles. It worked. But within about two years, the iron fittings touching the copper had badly corroded. That's galvanic corrosion: two different metals in seawater form a battery, and the iron is the side that gets eaten. The Navy's fix was to switch to copper-alloy bolts, and by around 1780 it had coppered the fleet. Coppered ships needed less time in dock for cleaning and repairs, so they could stay on station longer.

The copper still wore away, though. So the Admiralty asked Humphry Davy to stop that. In 1824 he attached blocks of zinc or iron to the hull so they would corrode instead of the copper. This was early cathodic protection, and it worked: the copper stayed bright. Then the hulls fouled badly, with trials on ships such as HMS Samarang. **Meanwhile:**
**Postgres numbers its transactions with a 32-bit counter, and it will stop accepting writes rather than let that counter wrap around.**

**How it works.** Each row stores the ID of the transaction that wrote it (its xmin). The counter is 32 bits, about 4.29 billion values, and comparisons are circular: about 2.1 billion IDs count as "the past" and about 2.1 billion as "the future". If a row's xmin gets more than about 2^31 behind the current ID, it suddenly looks like it was written in the future, and the row disappears from every query. VACUUM prevents this by "freezing" old rows, marking them as visible to everyone forever. If freezing falls behind, Postgres warns at 40M IDs remaining. Close to the limit it refuses to hand out new transaction IDs at all, which means the database stops taking writes. The settings involved are `autovacuum_freeze_max_age` (default 200M) and, since PG14, `vacuum_failsafe_age` (1.6B).

That is what took down Sentry in 2015 and Mandrill (Mailchimp) in 2019. Both were write-heavy, and in both vacuum couldn't keep up with freezing. Mandrill's outage lasted about a day.

**Why it matters for your migration.** It affects you in two places:

- **Old side (PG13), right now:** each initial table-sync COPY runs inside one long transaction with a snapshot. While a large table is copying, often for hours, that snapshot stops vacuum on the publisher from freezing or cleaning up anything newer than it. The logical slot also holds back `catalog_xmin`. If the PG13 cluster was already old in XID terms, those 90 minutes are when it gets closer to the limit. Quick check: `SELECT datname, age(datfrozenxid) FROM pg_database;` and `SELECT slot_name, age(catalog_xmin) FROM pg_replication_slots;`
- **New side (PG17), later:** logical replication re-inserts all 3 TB, so every row gets a fresh, young xmin from the new cluster's counter. The new database looks perfectly young, but all of that data was written in the same short window, so it will reach freeze age at about the same time. That means one large anti-wraparound vacuum pass across 3 TB, at a time you don't choose. Running `VACUUM (FREEZE, ANALYZE)` after the sync and before traffic grows pays that cost on your schedule. You need the ANALYZE anyway, because planner statistics aren't copied over.

**Meanwhile:**
**Postgres already counts transactions in 64 bits internally. The problem is fitting that into the bytes each row stores on disk.**

**How it works.** Since PG12 the server tracks a `FullTransactionId` internally: a 32-bit epoch plus the 32-bit XID. Every row, though, still carries 32-bit `xmin` and `xmax` in a 23-byte header. Making both fields 64-bit adds 8 bytes to every row version. For narrow tables, like event logs or join tables with ~40-byte rows, that's around 15–20% more heap, and more I/O and cache pressure with it.

The main patch line, started by Alexander Korotkov around 2017 and carried on by Postgres Pro engineers (Aleksander Alekseev, Maxim Orlov, Pavel Borisov), avoids the per-row cost. It stores a 64-bit "XID base" once per 8 KB page and keeps 32-bit offsets in each row. The catch is the upgrade path. Pages written by older versions have no room reserved for that base, and the patch needs `pg_upgrade --link` (minutes, no page rewrites) to keep working on multi-TB clusters. A format that forces every page to be rewritten on upgrade is effectively a dump/restore. So the work has been landing in pieces: SLRU page numbers went 64-bit in PG17 (I'm fairly sure of the version), and the heap format change is still out of core. Postgres Pro's commercial fork already ships it.

**The twist.** 64-bit XIDs don't remove the need for vacuum. Old XIDs still have to be resolved before the commit log (`pg_xact`) can be truncated, and freezing still feeds the visibility map that index-only scans rely on. What changes is the failure mode. Today, falling behind on freezing ends with the database refusing writes. With 64-bit XIDs, the commit log and bloat just keep growing on disk. It's the same unpaid work, but it shows up as a capacity alert instead of an outage.

**For you:** PG17 is still 32-bit on disk, so the post-sync `VACUUM (FREEZE, ANALYZE)` advice stands.

1) **Deeper**: multixacts, the second 32-bit counter, which wraps separately and has caused its own outages. Row locks like `SELECT ... FOR SHARE` and foreign-key checks consume it.
2) **Sideways**: why Oracle and MySQL/InnoDB never had this failure. They use undo logs instead of keeping old row versions in the table, which trades it for a different one: "snapshot too old".
3) **Wildcard**: the Royal Navy's ship rating system, and how "first-rate" stuck in English long after anyone counted guns.
