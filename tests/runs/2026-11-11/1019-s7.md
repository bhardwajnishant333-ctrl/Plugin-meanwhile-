**Your eager-to-lazy migration may already be half done in a way you can't see: in Kotlin, a `@ManyToOne(fetch = LAZY)` can quietly keep loading eagerly.**

**How:** for a lazy to-one association, Hibernate gives you a stand-in object (a proxy) in place of the real one. It builds that proxy by subclassing your entity at runtime. Kotlin classes are `final` by default, so Hibernate can't subclass them. When that happens, Hibernate doesn't throw an error. It just loads the related row right away and moves on. Collections (`@OneToMany`) don't have this problem, because Hibernate wraps the collection itself and never needs to subclass anything. The usual fix is the `kotlin("plugin.jpa")` plugin plus an `allOpen` block for `@Entity`, `@MappedSuperclass` and `@Embeddable`. Spring Initializr adds this for Kotlin JPA projects, but older or hand-written builds often don't have it. Also, `plugin.spring` alone does **not** open entities. I'm confident about the mechanism. How loudly your Hibernate version warns about it varies, so check your build file and logs rather than taking my word for it.

**What's happening:** `partService.findAll()` runs inside the service's transaction. When it returns, the transaction and the Hibernate Session close. `part.supplier` is now a lazy proxy that was never loaded. With `open-in-view=false` there's no Session in the controller, so the first `.name` call throws. The test passed before only because EAGER loaded the supplier up front. (Good news from the stack trace: `Supplier$HibernateProxy` means Hibernate could build the proxy, so your entities are correctly open. That's the Kotlin trap from earlier, and you've already avoided it.)

**Fix:** load the supplier in the query itself, and build the DTO inside the transaction.

```kotlin
interface PartRepository : JpaRepository<Part, Long> {
    @Query("select p from Part p left join fetch p.supplier")
    fun findAllWithSupplier(): List<Part>
}
```

```kotlin
@Service
class PartService(private val parts: PartRepository) {
    @Transactional(readOnly = true)
    fun listParts(): List<PartDto> =
        parts.findAllWithSupplier().map { it.toDto() }
}
```

Then the controller just returns `partService.listParts()`, and `toDto` moves out of `PartController` into the service or a mapper.

- Use `left join` so parts with no supplier still come back. If `supplier` is required, either kind of join works.
- If you'd rather keep `findAll()`, put `@EntityGraph(attributePaths = ["supplier"])` on an overridden `findAll()` in the repository. It does the same thing.
- Building the DTO inside `@Transactional` **without** the fetch join would also stop the exception, but you'd get N+1 queries (one more query per supplier). That's the problem lazy loading was supposed to solve.

**Don't** fix it by turning `open-in-view` back on or setting `hibernate.enable_lazy_load_no_trans=true`. Both hide this error by opening extra sessions and bring the N+1 queries back without telling you.

**Expect more of these:** every place that reads a lazy association after the service returns will break the same way. That means controllers, Jackson serializing entities directly, `toString` and log lines. Have Claude search for entity fields read in `api/`, and check that no controller returns an entity directly.
