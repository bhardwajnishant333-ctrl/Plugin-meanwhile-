**F1 doesn't time laps. It timestamps crossings and subtracts.**

Every car carries a transponder. It's a small radio beacon fitted at a fixed spot on the chassis. Cut into the track surface are timing loops, wires that pick up the transponder as it passes over. There's one at the start/finish line and one at each of the two sector boundaries, which gives the three sectors on your TV graphic. Each circuit also has many more "mini-sector" loops. Those drive the purple and green mini-sector colours on the F1 live timing app. The exact count varies by track, and I'm not sure of a typical number, so I won't guess one.

No clock runs from "go" on each lap. Each loop records the moment a transponder passes it, and every number you see comes from subtracting those timestamps afterwards:
- **Lap time** = this crossing of the finish loop minus the previous one.
- **Sector time** = the gap between two neighbouring loops.
- **Gaps on the tower** = your crossing minus the car ahead's crossing at the same loop.

The transponder sits in the same place every lap, so its distance from the nose cancels out of a lap time. The system only has to be consistent with itself, not exact about where the car's nose is. Timing also has a backup source so data isn't lost if the main feed drops out. I don't know its exact specs well enough to quote them.

**The twist:** the official result is a list of events. Lap times, sectors, intervals and even the Jerez tiebreak ("who set it first") are all just views computed from those raw crossing timestamps. The duration is derived. The event is the thing that actually happened.

**For your app:** you're logging durations off the TV graphic, which is downstream of all this. If you ever add sectors or gaps between cars, think about storing crossing events (car, loop, timestamp) as your SwiftData model and computing laps from them. That's F1's own design, and it means a typo in one sector can't quietly disagree with the lap total. It's worth a look once the migration is done, not mid-run.

**What the error means:** `LogLapView` reads `@Environment(\.modelContext)`, but no `ModelContainer` that knows about `LapEntry` is attached above it. When that happens, SwiftUI hands the view a default context with no container behind it. Nothing goes wrong until the first `insert`, at `saveLap()` line 58. This is very common mid-migration: the Core Data `.environment(\.managedObjectContext, …)` gets removed before the SwiftData container is wired in.

**Check these, most likely first:**

1. **The container isn't attached to the root.** In `LapLoggerApp`:
   ```swift
   WindowGroup {
       ContentView()
   }
   .modelContainer(for: LapEntry.self)   // or for: [LapEntry.self, Session.self, ...]
   ```
   If it's missing, or sits on a sibling view instead of an ancestor of `LogLapView`, that's your crash.

2. **`LapEntry` isn't in the schema.** If the container is built by hand (`ModelContainer(for: Schema([...]))`), make sure `LapEntry` is in the list. The same goes for any `VersionedSchema.models` array if Claude set up a migration plan.

3. **The container gets deallocated.** Something like `ModelContext(try ModelContainer(for: LapEntry.self))` created inline, or a container held in a local variable, gets freed right away, and the context left behind has no container. Keep the container in a `let` property on the App struct, or anywhere long-lived.

4. **A Core Data leftover.** Look for `.environment(\.managedObjectContext, …)` or a `PersistenceController` still being injected where `.modelContainer` should be.

5. **The crash happens only in previews or a sheet.** Add `.modelContainer(for: LapEntry.self, inMemory: true)` to the preview. A sheet presented from a separate window or scene also needs the modifier.
