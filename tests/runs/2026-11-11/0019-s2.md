Hi Priya. Your conversion might be making some charts flicker, and the code will look exactly the same as before.

**What changes:** `componentDidMount` and `componentDidUpdate` never ran "after render" the way most people picture it. They run synchronously in React's commit phase, before the browser paints. The old React docs said so directly: calling `setState()` in `componentDidMount` "will trigger an extra rendering, but it will happen before the browser updates the screen." The user never saw the first version.

The usual hooks translation is `useEffect`, but its timing is different. It's a passive effect, and React normally runs it *after* paint. The hook that actually matches the class lifecycles is `useLayoutEffect`. The React docs used to say it "fires in the same phase as componentDidMount and componentDidUpdate."

**Why it matters for a dashboard:** charts often measure their container on mount, using `getBoundingClientRect` or `offsetWidth`, then `setState({ width })`. In a class that cost nothing. Move it into `useEffect` and it can paint twice: once at the wrong width, then again at the right one. That shows up as a one-frame jump or a chart that briefly squeezes, and it's often only visible on slower machines.

One complication: since React 18, effects caused by a discrete user input, like a click, run synchronously before paint. So the flicker can appear on page load but not when you click around to test. It can look fixed while it isn't.

**Quick check when the run finishes:** search the diff for `useEffect` blocks that read layout (rect, offset, scroll, clientWidth) and then set state. Those are the ones to switch to `useLayoutEffect`.

**Meanwhile:**
In 1978 a grandmaster lost a bet that he could win the textbook "won" endgame, queen vs. rook, against a computer.

**What happened:** Ken Thompson (who co-created Unix) built Belle, a chess machine, and gave it a database of every queen vs. rook position worked out backwards from checkmate. That means its defence wasn't a strategy. It was the proven best move every time. Walter Browne, a six-time US champion, bet he could beat it with the queen within the 50-move limit. In his first session he couldn't. He went home, studied how the database defended, came back, and checkmated it on the 50th move, the last one allowed. That's the commonly told version. I'm confident about the outline but not sure of the exact payout.

**Why a grandmaster struggled:** human defenders keep the rook next to their king for protection. The database did the opposite. It moved the rook far away to awkward squares and kept checking from angles no textbook teaches. Every move was legal and none of them looked "correct" to a human, but it was the best defence possible. Browne wasn't up against a stronger player. He was up against a defence that human chess knowledge had never mapped.

**The bigger story:** a few years later Thompson's databases showed that two bishops vs. a knight, considered a draw since Kling and Horwitz analysed it in 1851, is usually a win, sometimes taking more than 50 moves. FIDE extended the 50-move rule for certain endgames, then dropped the exceptions in 1992. Over a century of agreement among experts was wrong because nobody could search the whole space.

**The takeaway:** a "won" position you've only tested against sensible opposition isn't proven. The opponent who checks everything finds the lines you never considered. Tests of your own code have the same blind spot, because they defend the way you would.

**Meanwhile:**
Retrograde analysis solves endgames perfectly using only the rules of how pieces move. It has no idea what a good move is.

**How it works (queen vs. rook as the example):**
1. **List every position.** Every legal placement of the four pieces, with either side to move. Board symmetry cuts that down a lot. Without pawns, the two kings can only be placed in 462 genuinely different ways.
2. **Label the endings.** Every position where the side to move is checkmated is "lost in 0".
3. **Work backwards.** If any move from a position reaches "lost in n" for the opponent, that position is "won in n+1". If every move from a position reaches a win for the opponent, it's "lost". Instead of trying every forward move, the program generates "un-moves" backwards from positions it has already labelled.
4. **Repeat until nothing changes.** Every position that never got a label is a draw.

That's the whole method. There's no evaluation, no strategy and no idea that a king should stay near its rook. It's dynamic programming over a graph, repeated until nothing changes. Browne's opponent was this procedure.

**Scale:** this is how every endgame tablebase is built. The Lomonosov tables of 2012 solved all positions with seven pieces. They're where the 549-move checkmate comes from, and they took around 140 TB. Ronald de Man's Syzygy format, which engines use today, stores the seven-piece set in about 17 TB. I'm sure of the order of magnitude, less sure of the exact figures.

**The catch:** a tablebase gives you a perfect answer with no explanation. It tells you which move wins but not why. People who study endgames, John Nunn most famously, spent years reading the databases to pull out rules a human can use. So the work splits in two: the machine proves the answer, and a person turns it into something others can understand. That second step doesn't happen on its own.
