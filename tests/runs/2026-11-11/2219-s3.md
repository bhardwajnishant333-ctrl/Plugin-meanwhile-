**Postgres can only count to about 4 billion, so every row needs a "frozen" stamp before the transaction counter laps it.**

Each transaction gets a 32-bit ID, and every row records the ID of the transaction that wrote it. IDs are compared in a circle: about 2.1 billion IDs count as "the past" and about 2.1 billion as "the future." If a row's ID gets more than about 2 billion transactions old without being marked frozen (a VACUUM job does that), it would seem to have been written in the future and would quietly disappear from queries. To prevent this, Postgres forces a freeze vacuum on any table whose oldest unfrozen ID passes `autovacuum_freeze_max_age` (200 million by default). It starts printing warnings about 40 million IDs before the limit. With only a few million left, it refuses to start new transactions that write anything until someone vacuums. This has caused real outages: Sentry wrote up theirs in 2015, and Mailchimp's Mandrill was down for about a day in February 2019.

The twist for your migration: pg_dump and pg_restore don't copy that history over. The new CNPG cluster starts its counter fresh, so any old freeze backlog is gone. But every table is restored within the same couple of hours, so they all start the clock together. Without other action, they all cross the 200 million mark around the same time later and their forced vacuums arrive in one burst. Running `VACUUM (FREEZE, ANALYZE)` once after the restore spreads that cost out ahead of time. The ANALYZE matters on its own too: pg_dump from 14 doesn't carry planner statistics, so the new 16 cluster starts with none until autovacuum gets to it.

**Meanwhile:**
**At 03:14:07 UTC on 19 January 2038, a 32-bit Unix clock jumps back to 13 December 1901.**

Unix time counts seconds since 1 January 1970. Stored as a signed 32-bit integer, the largest value it can hold is 2,147,483,647, which is that exact second in 2038. One second later the number overflows, goes negative, and the date reads as 1901. The fix is a 64-bit `time_t`, and most of it is done. Linux 5.6 (2020) let 32-bit systems use 64-bit time. glibc 2.34 added the `_TIME_BITS=64` option. Debian rebuilt its 32-bit ARM ports on 64-bit time in 2024. What's still exposed is data stored in fixed formats, not the clocks themselves. MySQL's `TIMESTAMP` type still ends at 2038-01-19 03:14:07. Older ext4 filesystems with 128-byte inodes stop at 2038 too, while XFS only got its "bigtime" extension in Linux 5.10. Then there are embedded devices nobody will ever reflash: PLCs, meters, cars, medical devices.

The twist: 2038 isn't one future date. It arrives the moment any program calculates a date past it. A timeout, a certificate expiry, a 20-year bond, or a "never expires" placeholder of 2^31 seconds all wrapped years ago. One widely told example: AOLserver reportedly crashed in 2006 because a default timeout of one billion seconds landed past 2038. I'm confident about the mechanism but not certain of that story's details. Your setup is safe: Postgres `timestamp` is 64-bit and runs to 294276 AD, and Talos is 64-bit throughout.
