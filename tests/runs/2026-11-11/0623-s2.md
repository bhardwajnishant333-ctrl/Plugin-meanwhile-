**Your new Zustand store has no way to do a "transition", and neither did Redux.**

React 18 added concurrent rendering, which let React pause a render halfway through. That created a problem called "tearing": a store outside React could change mid-render, so half your components showed the old playlist and half showed the new one. React's fix was `useSyncExternalStore`. It works by making any external-store update render synchronously, all at once, so tearing can't happen. Zustand v4 and up is built on it, and so is react-redux since v8.

So the migration doesn't change much here, but it hides a catch. If you wrap a store update in `startTransition`, expecting React to keep the UI responsive while the heavy work renders, React quietly ignores that and does a normal blocking render. The React docs say this outright. Only state that React owns, like `useState` or `useReducer`, can be a true non-blocking transition. For a scheduler that might re-render a whole week of slots when you drag one show, that's where jank would come from.

**A chess match where each move took weeks named an opening people still play 200 years later.**

From 1824 to 1828, the Edinburgh Chess Club and the London Chess Club played each other entirely by post, with moves going back and forth by mail coach. Each side was a committee, so every move was argued over before it was sent. It took about four years to finish five games. Edinburgh won 2 wins to 1, with 2 draws. **Meanwhile:**
**At the top of ICCF the most useful signal isn't an engine's score. It's two engines disagreeing.**

Engines go wrong in three main ways.
- **Fortresses.** One side is up material but the position is locked: blocked pawns, opposite-colored bishops, no way to break through. The engine searches millions of moves, never sees a win, and still shows something like +2 because its scoring counts the extra material. Humans recognize "no way in" by looking at the structure. Engines have to search it out, and the search can't prove that nothing exists.
- **The horizon.** Long plans, like slowly moving a king across the board or a pawn break 30 moves away, sit past the depth the engine searches. Before it reaches them it judges the position by feel, and the feel can be confidently wrong.
- **Different kinds of engines see different things.** Stockfish searches very deep and uses a fast neural network to score positions. Leela uses a much heavier network with far less searching. They tend to disagree most in closed, strategic positions, which are exactly where neither can be trusted.

So strong correspondence players don't ask "what's the best move?" They run several engines, look for the positions where those engines disagree, and spend their own thinking time there. They also pick openings that lead to positions the engines call equal but that are hard to play correctly for months on end. Most games at the top are draws. The wins tend to come from a judgment call the engines got wrong.

The twist for right now: when Claude finishes the Zustand migration, the places most likely to hide a bug are where two reasonable reviewers would disagree. Selector equality, stale closures in subscriptions, and actions that used to run in the reducer's order are the "closed positions" of a state migration.
