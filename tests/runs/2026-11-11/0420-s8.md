**Mira can fade by 6 magnitudes or more to your eye, about a 250-fold drop, while its total energy output falls by only around a factor of 2.**

Two things make up the gap.

First, a Mira-type star is cool, roughly 2,000 to 3,000 K, so most of its light is already infrared. When it cools a little, more of its output moves out of the visible band, and the band your eye sees takes most of the loss.

Second, titanium oxide forms in its outer atmosphere. When the star is at its coolest, molecules form there that absorb visible light very strongly. So the star mostly gets hidden behind its own atmosphere rather than actually getting weaker. The full cycle runs about 332 days for Mira itself. Fabricius first recorded its change in 1596.

**The twist:** what your binocular estimates measure is mostly the star's atmospheric chemistry, not its power output. Plotted in infrared, the same star's light curve is far flatter. That is a big reason amateur visual records stay useful to professionals: the visible band is where the dramatic changes show up.

**Meanwhile:**
**In Laravel, a queued job can run twice even though nothing failed. It only has to run longer than one config value, `retry_after`.**

Here is how the Redis driver handles it. When a worker picks up a job, Laravel doesn't delete it. It moves the job into a `queues:default:reserved` sorted set, scored with an expiry time of now + `retry_after` (90 seconds in the default config). Every time any worker asks for a job, Laravel first moves expired jobs from that set back onto the main queue. So if your booking job is still running at second 91, maybe because of a slow payment call or a stuck email, a second worker takes it and runs it again, while the first one is still going.

Laravel's docs state the rule directly: the worker's `--timeout` must be several seconds shorter than `retry_after`. Then the first worker gets killed before the job can be handed out a second time. The database driver works the same way, so check that the new `redis` block in `config/queue.php` keeps a sensible value and doesn't just fall back to the default.

**The twist:** no setting gets you to "exactly once." Queues promise at-least-once delivery, and a crashed worker will always produce a retry. The real fix is to make the booking job safe to run twice. One way is a unique index on the booking row, so the second insert fails cleanly instead of selling a slot twice.
