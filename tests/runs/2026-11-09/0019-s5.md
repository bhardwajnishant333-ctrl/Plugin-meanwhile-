**Meanwhile:**
Your engine can't implement `serde::Serialize` for `glam::Vec3`, even though both crates are sitting right there in your dependency tree. That rule is the compiler's version of the anemones' bare border strip.

Rust promises that a program has at most one implementation of any given trait for any given type. This is called coherence. The orphan rule is how it keeps that promise one crate at a time. You may write `impl Trait for Type` only if your crate defines the trait or the type. Rust 1.41 (2020, RFC 2451) loosened this a little: a foreign trait can be implemented for a foreign type when one of your local types appears early enough among the type parameters. The classic reason for the rule is the "hashtable problem". If crate A and crate B each wrote their own `Hash` for the same type, and both ended up in one `HashMap`, keys hashed one way would be looked up the other way and the map would silently break. Haskell allows these "orphan instances" and only warns about them. Rust refuses to compile them.

The twist: protecting that global invariant pushes cooperation upstream. The library author has to plan ahead for your needs, which is why `glam` ships a `serde` feature flag. Downstream, your escape hatch is the newtype `struct MyVec3(glam::Vec3)`. It wraps the same data under a new identity, like a clone that counts as a stranger. The general fix, specialization, was proposed in RFC 1210 in 2015 and as far as I know is still unstable, mainly because of soundness holes involving lifetimes.
