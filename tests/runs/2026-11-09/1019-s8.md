**Meanwhile:**
**Taking a distributed lock is the easy part. The hard part is that the holder can stall or die while the lock still says it's busy.**

Every distributed lock rests on one atomic step: write this key only if it doesn't exist (or only if it still has the value I last saw). etcd does this with transactions that compare a key's revision, ZooKeeper with ephemeral sequential znodes, Postgres advisory locks with a row in shared memory. S3 got the same ability in 2024, and that's why Terraform no longer needs DynamoDB.

The trouble starts when the holder stops responding. Most systems give the lock a lease that expires, so a crashed holder can't block everyone forever. Martin Kleppmann's 2016 post, "How to do distributed locking," showed what goes wrong. Client A takes the lease, then sits in a long GC pause. The lease runs out, client B takes the lock and writes. Then A wakes up still believing it holds the lock and writes as well. A lease alone can't stop that. His fix is the **fencing token**: every time the lock is granted, the holder also gets a number that keeps going up, and the storage refuses any write carrying a lower number than one it has already seen. The storage itself enforces the lock, so a client that's out of date can't do damage.

**The twist, for your split:** Terraform's state lock goes the other way. It has no lease, so it never expires, which is why `terraform force-unlock` exists. And as far as I know, the state write isn't fenced. If someone force-unlocks because an apply looks hung, but it was only slow (a long RDS modify, a stuck CI runner), both runs can write state. Last write wins and silently overwrites the other. Splitting into modules means more state files, so more locks, so more chances someone runs force-unlock. A good rule for the runbook: confirm the holder is actually dead (check the lock's `Who`/`Created` info and the CI job) before force-unlocking. Don't go by how long it's been.
