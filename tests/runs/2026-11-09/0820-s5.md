**Meanwhile:** Your Phoenix app already hot-swaps code many times a day, just never in production.

The mechanism: the BEAM can hold two versions of a module at once, "current" and "old." A fully qualified call (`MyMod.fun()`) always goes to the current version. A process already running old code stays on it until its next fully qualified call. If you load a third version, the old one is purged, and any process still running it gets killed. OTP builds release upgrades on top of this. An `.appup`/`.relup` file describes the steps: suspend processes with `sys:suspend`, load the new modules, run `code_change/3` to convert each process's state to the new shape, then resume. Ericsson designed it this way so a telephone switch could be upgraded without dropping calls.

Few Phoenix teams use it because writing appups by hand for every release is fiddly, and the state migrations are easy to get wrong. Mix releases (Elixir 1.9+) also don't support hot upgrades out of the box. So most teams do rolling or blue-green deploys and let LiveView sockets reconnect and run `mount` again.

The twist: in dev you use it constantly. `Phoenix.CodeReloader` recompiles changed files and loads the new modules into the running VM when a request comes in. That's why your server doesn't restart when you save a file. The two-version rule explains a dev quirk too: a long-running process sitting in a `receive` loop can keep old code until it makes a fully qualified call.

1) Deeper: what `code_change/3` actually has to do, and why the appup is where hot upgrades go wrong
