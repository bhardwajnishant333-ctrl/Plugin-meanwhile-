Your upgrade can produce a unique index that holds two copies of the same key. Postgres won't throw an error until the REINDEX you're planning to run anyway, and then the REINDEX itself fails.

**How it happens:** Postgres doesn't sort text itself in the default setup. It hands that to the OS C library, glibc. glibc 2.28 (released August 2018, shipped in Debian 10 and RHEL 8) rewrote the sort rules for most locales, including en_US.UTF-8. Strings with spaces, hyphens and punctuation changed order. `pg_upgrade --link` keeps your old index files byte for byte, in the old sort order. If the new image has a different glibc than the old one, a B-tree search for a key can descend to the wrong leaf page and report the key as missing when it's there. Reads silently skip rows. Worse, an INSERT into a unique index can miss the existing key and write a second copy. The PostgreSQL wiki page "Locale data changes" covers this. Whether it affects you depends on whether your PG12 and PG16 images use different glibc versions. Check that first: compare `ldd --version` in both images. If they're the same, you're fine.

**The twist:** The REINDEX step only protects you if no writes happen before it finishes. If the app comes back up first, the duplicates can land early, and then `REINDEX` of that unique index fails with "could not create unique index ... is duplicated." Now you're cleaning up data instead of finishing an upgrade. So order matters more than the reindex: keep writes off until the indexes on text columns are rebuilt, and rebuild those first. `amcheck`'s `bt_index_check(..., heapallindexed => true)` can tell you whether an index is affected before you trust it. Since PG15, Postgres records each database's collation version (`datcollversion`) and warns when it doesn't match the OS. That warning is how you'll notice this next time.

**Meanwhile:** The full REINDEX after a 12 → 16 upgrade is mostly optional. Only one group of indexes needs it to be correct, and a single query lists them.

**Finding them:** An index can only be affected if at least one of its columns uses a glibc (libc) collation other than C/POSIX. That's either an explicit libc collation, or the database default when the database itself uses libc. `pg_index.indcollation` stores one collation per index column, including expression columns, and 0 for columns that aren't text. Run this in each database:

```sql
SELECT i.indexrelid::regclass AS index,
       i.indrelid::regclass   AS tbl,
       pg_size_pretty(pg_relation_size(i.indexrelid)) AS size
FROM pg_index i
CROSS JOIN LATERAL unnest(i.indcollation) AS u(collid)
JOIN pg_collation c ON c.oid = u.collid
CROSS JOIN (SELECT datlocprovider, datcollate
            FROM pg_database WHERE datname = current_database()) d
WHERE (c.collprovider = 'c' AND c.collcollate NOT IN ('C','POSIX'))
   OR (c.collprovider = 'd' AND d.datlocprovider = 'c'
       AND d.datcollate NOT IN ('C','POSIX'))
GROUP BY 1, 2, i.indexrelid
ORDER BY pg_relation_size(i.indexrelid) DESC;
```

One gap: a partial index whose WHERE clause compares text won't show up here, because the predicate's collation isn't stored in `indcollation`. Those are rare, but search the index definitions for them. I haven't run this exact query myself, so test it on a replica first.

**The twist:** Look at what the rest of the reindex is for. pg_upgrade doesn't require rebuilding B-tree indexes from 12 to 16. The one real gain is **deduplication**, a PG13 feature. The PG13 release notes say indexes carried over by pg_upgrade only get it after a REINDEX. That can shrink indexes on columns with many repeated values a lot, but it's about size, not correctness. So the safe order on a 2 TB cluster is:

1. Rebuild the indexes this query returns, before the app writes. This step is about correctness, and only matters if glibc changed between images.
2. ANALYZE right away. pg_upgrade on 16 does **not** carry planner statistics over (that only arrived in PG18). Until it runs, the planner is working without stats, so `vacuumdb --analyze-in-stages` gives you rough stats quickly. This step decides whether your p99 latency survives the first hour.
3. Run `REINDEX ... CONCURRENTLY` on everything else whenever convenient, largest indexes on low-variety columns first.

If you check what the agent is doing, see whether it's reindexing everything in one blocking pass. That would be the slowest version of a step that's mostly optional.

1. **Deeper:** how B-tree deduplication actually works, and how to estimate the gain before rebuilding (`pgstattuple`, `bt_metap`'s `allequalimage`)
2. **Sideways:** Mehmed II, 1453: roughly 70 ships dragged over the Galata hills to get around the Golden Horn chain
3. **Wildcard:** the Ottoman *menzilhane* relay-station network. It was a courier system that worked like a message queue, with stations at fixed distances and fresh horses kept ready
