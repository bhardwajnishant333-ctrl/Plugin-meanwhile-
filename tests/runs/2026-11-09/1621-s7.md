**Meanwhile:** **In Laravel, January 31 plus one month is March 2.**

`Carbon::parse('2024-01-31')->addMonth()` returns **2024-03-02**. Carbon runs on PHP's DateTime, which bumps the month to "February 31" and then rolls the extra days forward: 2024 is a leap year, so Feb 29 + 2 = March 2. In 2025 you get March 3. Carbon also has `addMonthNoOverflow()`, which clamps to Feb 29 instead.

The software world can't agree on what "same day next month" means. There are three conventions:
- **Overflow** (PHP and Carbon's default `addMonth`): Jan 31 → Mar 2
- **Clamp** (Carbon `NoOverflow`, Postgres `+ interval '1 month'`): Jan 31 → Feb 29
- **Skip** (RFC 5545, the iCalendar standard): "monthly on the 31st" gives no February date at all. The spec says invalid dates MUST be ignored, so you get only 7 appointments a year.

**The twist:** clamping still causes drift if each date is computed from the previous one. Jan 31 → Feb 29 → Mar 29 → Apr 29... After one short month, the 31st becomes the 29th for good. The fix is to compute occurrence *n* from the original anchor date (start + n months), never from the previous occurrence. Worth checking your agent's diff for a loop that does `$date = $date->addMonth()`.

**Meanwhile:** **A "9:00 every Tuesday" appointment saved as UTC is a bug that waits months to show up.**

Here's how it happens. In New York in winter, 9:00 local is 14:00 UTC. The agent expands the series and saves `14:00Z` for every Tuesday. In March the clocks spring forward, and 14:00 UTC now displays as **10:00**. The appointment didn't move, but the clock did. Laravel makes this easy to miss: `config/app.php` defaults to `'timezone' => 'UTC'`, and a plain `datetime` column stores no zone at all.

There are also two edge cases where a local time doesn't map to exactly one moment:
- **Spring forward:** 2:30 a.m. doesn't exist that day. RFC 5545 says recurring instances at a nonexistent local time are skipped.
- **Fall back:** 1:30 a.m. happens twice. Which one do you mean?

A vet clinic probably never books at 2 a.m. The first problem is the one that will bite.

**The twist:** UTC can't make a future appointment safe, because time-zone rules are set by governments and they change. Mexico abolished most daylight saving time in October 2022, with only weeks of warning. Any future appointment that had been converted to UTC under the old rules was now off by an hour. The IANA time-zone database ships several updates a year to keep up.

So the rule is:
- **Past events:** store the instant in UTC. It happened, and it's fixed.
- **Future events:** store the intent: wall-clock time plus an IANA zone, like `09:00` + `America/New_York`. Work out the UTC time for each occurrence as late as you can.

**Meanwhile:** Back to code. The bug is on line 44.

**Cause:** `new RecurrenceRule($data['rule'])` builds the model in memory but never saves it, so `$rule->id` is `null`. Then `?? 0` on line 52 hides that and inserts `recurrence_rule_id = 0`. No rule has id 0, so MySQL rejects the foreign key.

**Fix:** save the rule first, drop the `?? 0`, and wrap the whole series in a transaction so you never end up with half a series:

```php
use Illuminate\Support\Facades\DB;

return DB::transaction(function () use ($data) {
    $rule = RecurrenceRule::create($data['rule']);   // was: new RecurrenceRule(...)

    $occurrences = $this->expander->expand($rule, $data['starts_at'], $data['count']);

    foreach ($occurrences as $when) {
        Appointment::create([
            'pet_id'             => $data['pet_id'],
            'vet_id'             => $data['vet_id'],
            'starts_at'          => $when,
            'recurrence_rule_id' => $rule->id,        // no "?? 0"
        ]);
    }

    return $rule;
});
```

If `RecurrenceRule` has an `appointments()` hasMany relation, `$rule->appointments()->create([...])` sets the foreign key for you.
