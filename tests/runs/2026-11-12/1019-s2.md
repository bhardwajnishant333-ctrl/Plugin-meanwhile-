**There are chess positions that are a forced win, with a computer proof, that the rules still score as a draw.**

**How:** Endgame tablebases aren't built by searching forward. They're built backwards, by retrograde analysis. You list every checkmate position. Then you mark every position where one move reaches a mate as "win in 1". Next you mark positions where every reply runs into one of those as "loss in 1". You repeat until nothing changes. Ken Thompson did this for 5-piece endings in the 1980s. The Lomonosov tables at Moscow State University covered all 7-piece positions in 2012, at about 140 TB. They found a position where the winning side needs 549 moves to force mate, with perfect defence. Bojun Guo finished the Syzygy 7-piece tables in 2018, and those count moves to the next capture or pawn move instead of moves to mate.

**The twist:** The 50-move rule lets either player claim a draw after 50 moves by each side with no capture and no pawn move. So some proven wins can't actually be won over the board. Syzygy has an official label for them: a **"cursed win"**. The mirror case, a lost position the 50-move rule saves, is a **"blessed loss"**. Engines have to track two truths at once, what the position is worth and what the rules let you collect. Thompson's results made FIDE extend the move limit for certain endings in the late 1980s. As far as I remember, they dropped those exceptions around 1992 because the wins were too deep for humans to follow anyway.

**TanStack Query treats your data as stale the moment it arrives. That's the default, and it comes from a 2010 HTTP spec.**

**How:** Mark Nottingham wrote RFC 5861 in May 2010. It added two Cache-Control directives. `stale-while-revalidate` lets a cache serve an expired response right away while it fetches a fresh one in the background. `stale-if-error` lets it keep serving the old response if the origin fails. The idea was that a slightly old page now beats a correct page after a spinner. Vercel's SWR library (2019) is named after the first directive. TanStack Query builds its model on the same idea. `staleTime` defaults to 0, so cached data counts as stale immediately. It's still shown, but the library refetches on mount, on window focus and on reconnect. A separate timer, `gcTime` (called `cacheTime` before v5), removes unused data after 5 minutes by default. The query key works like the URL in an HTTP cache: it's the cache's identity.

**The twist:** This changes the question from "where is this data stored?" to "how wrong am I willing to let it be?" With Redux, your store holds the data and it stays put until you change it. With TanStack Query, the server holds the data and your app only keeps a copy that ages. The practical effect for your migration: with the defaults, you'll likely see more network requests than under Redux, especially when people switch browser tabs. That's working as designed. You tune it by setting `staleTime` per query, chosen by how fast each piece of data really changes.

**Meanwhile:**
**Every `setQueryData` call is a small copy of your backend's logic, and it'll fall out of sync with the real one.**

**How:** `invalidateQueries({ queryKey: ['users'] })` doesn't touch any data. It marks every query whose key starts with `['users']` as stale. That includes `['users', { page: 2 }]` and `['users', { role: 'admin' }]`. By default it then refetches only the ones currently on screen (`refetchType: 'active'`). The rest refetch the next time they're shown. `setQueryData` writes to one exact key right away, with no network call. Say you change a user's role. To get the cache right by hand, you'd have to update every cached list page and filter combination. You'd also need to copy the server's sorting, totals, `updatedAt` stamps and permission side effects. Miss one key and that screen shows wrong data until something else refetches it.

**When `setQueryData` is the right tool:**
- The mutation returns the full updated entity, and you write it to that entity's own detail key. That's a copy, not a guess.
- Optimistic updates, using the pattern from the docs. In `onMutate`, call `cancelQueries` so a refetch already in flight can't overwrite your edit, save a snapshot with `getQueryData`, then write. In `onError`, put the snapshot back. In `onSettled`, call `invalidateQueries` so the server has the final say.

**The twist:** A Redux reducer is a hand-written cache edit. An agent migrating reducer by reducer is likely to turn each one into a `setQueryData` call. That moves the old class of bugs into the new library and makes it harder to spot. A quick check when the run finishes: count the `setQueryData` calls in the diff. Each one that isn't an optimistic update or a write of the full returned entity probably should be an `invalidateQueries` call.
