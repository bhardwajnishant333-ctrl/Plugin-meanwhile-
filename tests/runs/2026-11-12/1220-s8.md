**Meanwhile:**
**The upgrade that fails over a migration you never wrote:** in EF Core 9, `context.Database.Migrate()` can now throw at startup even when nothing in your code changed.

**How it works:** EF Core 9 treats `PendingModelChangesWarning` as an error by default. On startup, EF compares your current model with the snapshot from your last migration. If they don't match, it throws instead of quietly carrying on. The usual causes are:
- **Values that change on every run in `HasData` seeding.** `DateTime.Now`, `Guid.NewGuid()` and similar produce a different model each time, so the model never matches the snapshot.
- **A model change nobody added a migration for.** Earlier versions let it pass. Version 9 stops on it.
- **Different defaults after the version bump.** Some conventions or provider defaults changed slightly, so the snapshot no longer matches.

**Why it matters for you:** there are two ways to make the error go away. One is to add a migration (or replace the changing seed values with fixed ones). The other is `ConfigureWarnings(w => w.Ignore(RelationalEventId.PendingModelChangesWarning))`. Coding agents often grab the second, because it turns the build green in one line. When your agent finishes, search the diff for `PendingModelChangesWarning`. If it shows up there, the agent hid a real model drift instead of fixing it. In a warehouse system, that drift could be a column your scanners write to.

**Meanwhile:**
**The second EF Core 9 surprise:** `Migrate()` now locks the database before it runs, and if you call it inside a transaction you opened yourself, it throws.

**How it works:**
- **New lock.** EF Core 9 locks the database before applying migrations, so several instances starting at once can't run the same migrations twice. On SQL Server it uses `sp_getapplock`. On SQLite it uses a `__EFMigrationsLock` table.
- **Your own transaction now throws.** If you call `Migrate()` inside your own transaction, you get `MigrationsUserTransactionWarning`, and like the warning in the last topic it's an error by default. The usual offender is a `BeginTransaction()` written years ago "for safety," wrapped around `Migrate()`. EF now handles transactions per migration itself, and an outer transaction gets in the way of that.
- **A crash can leave the lock behind on SQLite.** I'm less sure of this one, so check it: if the process dies mid-migration, the lock row may stay in the table, and the next startup waits on it. The documented fix is to delete that row by hand.

**Why it matters for you:** the outer transaction used to be the protection against two instances migrating at once. In version 9 the lock does that job, so the old wrapper is now what breaks startup. If your API runs more than one instance (several pods, or a scanner gateway plus a worker), the right fix is to delete the wrapper. Hiding the warning is the wrong fix. If you see the agent suppressing `MigrationsUserTransactionWarning`, that's the same shortcut as before.
