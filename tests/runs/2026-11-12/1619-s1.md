**The oldest sea charts have the whole Mediterranean tilted about 9 degrees counterclockwise, and the tilt tells you how they were made.**

The Carta Pisana (c. 1275) is the oldest surviving portolan chart, and Pietro Vesconte's 1311 chart is the oldest one that's dated. Neither has latitude, longitude or a projection. They were built from sailors' compass bearings and distance estimates between harbours. Those coast-to-coast legs were stitched into a web, and the rhumb lines radiating from the wind roses were the drafting grid. The coastlines are surprisingly accurate locally, but the whole basin is rotated. The usual explanation is magnetic declination: the compass pointed several degrees east of true north, so every bearing carried the same error. Historians still debate how much of the tilt that accounts for.

**A straight GDScript-to-C# port can end up slower, and it happens where the C# talks to the engine.**

GDScript runs inside the engine, so when it calls an engine method like `set_cell` or reads a Godot `Array`, the call stays in the engine. C# runs in .NET, so every one of those calls crosses a managed-to-native boundary and its arguments get converted along the way. Godot's own docs warn that `Godot.Collections.Array` and `Dictionary` live in engine memory, so each access from C# is an interop call. For data that never needs to reach the engine, they recommend .NET collections like `List<T>`, plain arrays or `Dictionary<K,V>`. A quieter cost comes from passing string literals where the API wants a `StringName`, which converts the string on every call. That's why people cache `StringName`s.

**The twist:** a literal port changes where the cost is. If your agent turned GDScript arrays into `Godot.Collections.Array`, or kept calling `SetCell` inside the generation loop, it moved the hot path onto the boundary. C# is clearly faster for pure computation: BSP splits, cellular automata, flood fills and pathfinding over an `int[,]` grid. The pattern that works is to generate everything in plain .NET data and cross into the engine once at the end, painting the tilemap in a single pass. I don't have reliable per-call overhead numbers, so profile both versions rather than trusting either of us.

**Rogue's dungeons look random, but every level sits on the same hidden tic-tac-toe board.**

Michael Toy and Glenn Wichman wrote Rogue at UC Santa Cruz around 1980, and Ken Arnold joined later. They wanted a game that could still surprise its own authors. The screen was a fixed 80×24 terminal, so the generator split it into a 3×3 grid of nine slots. Each slot got either a room of random size and position or a "gone room", which is only a corridor junction. Corridors run only between neighbouring slots, so connectivity becomes a tiny graph problem: link the nine cells until everything is reachable, then maybe add a few extra corridors for loops. I'm confident about the 3×3 layout and the gone rooms. I'm less sure of the exact corridor-linking order in each version.

**The twist:** Rogue is the opposite of a portolan. A portolan builds its map by stitching local measurements together, so it drifts as a whole. Rogue fixes a coarse global frame first and puts all the randomness inside it, so the map can't drift, can't run off the screen, and is guaranteed connected for nearly free. Most of the variety in a level comes from a structure the player never notices.
