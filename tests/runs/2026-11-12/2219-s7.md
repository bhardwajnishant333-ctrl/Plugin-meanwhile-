**Meanwhile:**
**Java 21 runs a million threads on a handful of real ones, and in 2024 Netflix found that four stuck threads could freeze a whole service.**

Virtual threads (final in Java 21, JEP 444) run on a small pool of "carrier" platform threads, by default one per CPU core. When a virtual thread blocks on I/O, it normally steps off its carrier so another one can use it. On Java 21 there's an exception: if it blocks inside a `synchronized` block, it gets **pinned** and keeps hold of the carrier. In Netflix's case (their tech blog post "Java 21 Virtual Threads – Dude, Where's My Lock?", July 2024), every carrier ended up pinned by threads waiting on a lock. The thread that could release that lock was itself a virtual thread with no free carrier to run on. Throughput dropped to zero and nothing crashed. JDK 24 removed most of this pinning (JEP 491, March 2025), but you're moving to 21.

**The twist:** your port is safe on this front. Moving to Java 21 doesn't turn virtual threads on. Spring Boot only uses them if someone sets `spring.threads.virtual.enabled=true`. The risk shows up later, when someone flips that flag for a quick win. Your own code is probably fine, especially with coroutines. The pinning risk sits in dependencies you never read: JDBC drivers, connection pools, and older client libraries that use `synchronized` around blocking calls. If you ever enable it, run with `-Djdk.tracePinnedThreads=full` or watch the JFR event `jdk.VirtualThreadPinned` first.

**Meanwhile:**
**Your hawk comes from one of the only raptor species shown to hunt in coordinated groups. The paper that proved it was published in *Science* in 1988, and it reads a lot like a failover runbook.**

James Bednarz followed wild Harris's hawks in southeastern New Mexico ("Cooperative Hunting in Harris' Hawks", *Science* 239, 1988). Family groups of roughly 2–6 birds met on a perch at dawn, split up, and moved through the scrub in short leapfrogging flights. He described three tactics:

- **Surprise pounce:** several hawks converge on a rabbit from different directions at the same moment, so it has no clean way to escape.
- **Flush and ambush:** the rabbit goes into cover, one hawk goes in after it on foot or in a low dive, and the others wait at the exits.
- **Relay attack:** on a long chase, the lead hawk drops back and a fresh one takes over, swapping several times until the rabbit tires.

The economics are what made it a *Science* paper. A jackrabbit is too big and fast for one Harris's hawk to take reliably. Even after being split several ways, group kills gave each bird enough energy, and Bednarz found the per-bird payoff was best at around five hawks. (I'm confident about the tactics. Treat the exact optimal group size as approximate.)

**The twist:** the relay attack is leader rotation, not leader strength. No single hawk has to outlast the rabbit. The group only needs a handoff that's faster than the prey's recovery. That's the same reason a cluster with quick, cheap failover beats one heroic primary node. The design question becomes "how fast is the handoff?" rather than "how strong is the leader?" Your inventory service runs on the same principle when one pod dies mid-request and another picks it up before the order times out.

**Cause:** `AuditFilter` still uses `javax.servlet`. Spring Boot 3.3 runs on Tomcat 10.1, which only provides `jakarta.servlet`, so `javax.servlet.Filter` doesn't exist at runtime. The "required a bean of type `javax.servlet.http.HttpServletRequest`" part follows from the same problem. In Boot 2.7, Spring could inject a request-scoped `HttpServletRequest` proxy. In Boot 3 it only registers the `jakarta` type, so the `javax` one can't be found.

**1. Fix the filter.** Switch to jakarta, and don't inject the request through the constructor at all. A filter already receives the request in `doFilter`:

```kotlin
import jakarta.servlet.FilterChain
import jakarta.servlet.http.HttpServletRequest
import jakarta.servlet.http.HttpServletResponse
import org.springframework.stereotype.Component
import org.springframework.web.filter.OncePerRequestFilter

@Component
class AuditFilter(/* keep other deps, drop HttpServletRequest */) : OncePerRequestFilter() {
    override fun doFilterInternal(
        request: HttpServletRequest,
        response: HttpServletResponse,
        chain: FilterChain,
    ) {
        // audit logic using `request`
        chain.doFilter(request, response)
    }
}
```

**2. Find out why it still compiled.** If `javax.servlet` imports compile, something is still putting the old servlet API on your classpath. Check:

```
grep -rn "javax\.servlet" src/
./gradlew dependencies --configuration compileClasspath | grep -i servlet
./gradlew dependencies --configuration runtimeClasspath | grep -i servlet
```

Then run `./gradlew clean build` so stale compiled classes aren't confusing the result.

**3. ESAPI 2.5.0.0 is the most likely culprit.** It's built against `javax.servlet`, so any of its servlet-facing classes (`HTTPUtilities`, `SecurityWrapper`, and so on) will break on Boot 3. Newer ESAPI releases ship a Jakarta build under a `jakarta` classifier. I believe it starts at 2.5.2.0, but check Maven Central for the exact version:

```kotlin
implementation("org.owasp.esapi:esapi:<version>:jakarta")
```

If you only use ESAPI for output encoding, consider replacing it with the much smaller OWASP Java Encoder (`org.owasp.encoder:encoder`).

**4. Bucket4j 7.6.0 isn't causing this.** `bucket4j-core` has no servlet dependency and runs fine on Java 21. If you upgrade later, note that 8.x moved to the `com.bucket4j` group ID. That's a separate change, not part of this fix.

If there are more `javax` leftovers, OpenRewrite's Spring Boot 3.3 upgrade recipe can do the import rewrite mechanically and catch what the agent missed.
