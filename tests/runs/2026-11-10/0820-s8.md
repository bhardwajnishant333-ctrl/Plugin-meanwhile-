## Turn 1 — Meanwhile
**In 1944 the D-Day landing times were set partly by a machine made of brass pulleys, built on 1870s ideas.**

Every tide table you've used works the same way. Tides aren't predicted by simulating the ocean. They're predicted by adding up a set of cosine waves called harmonic constituents. Astronomy fixes the period of each wave. M2, the principal lunar wave, has a period of 12.42 hours. S2, the solar one, has exactly 12 hours. K1 and O1 are the daily waves. A local tide gauge records about a year of water levels, and least squares fits an amplitude and a phase for each constituent at that spot. To predict, you add the waves back together.

In 1872 Lord Kelvin built this as hardware. Each constituent is a crank turning at its own rate, and one wire running over all the pulleys adds them up. A pen draws the tide curve for a whole year in a few hours. The US version, nicknamed "Old Brass Brains," handled 37 constituents and was in use until the 1960s. For Overlord, Arthur Doodson at the Liverpool Tidal Institute ran these machines for the Normandy beaches. The reported story is that he got the harmonic constants under code names and wasn't told where they were.

**The twist:** the hard physics, like basin resonance, shelf friction and the shape of the coastline, never gets modeled. It all ends up inside each constituent's amplitude and phase. Fixed frequencies from astronomy plus fitted local constants beat first-principles simulation for about 150 years. That's why your tide app can be accurate to minutes while ocean models still have trouble with coastlines.

## Turn 2 — Meanwhile
**There's a proof that two machines can never be sure they agree, and your idempotency keys exist to work around it.**

The Two Generals problem was first described by Akkoyunlu, Ekanadham and Huber in 1975, and Jim Gray named it in 1978. Two armies must attack together. The only way they can talk is by messengers who might be captured. A sends "attack at dawn." B has to confirm it. Then A has to confirm the confirmation, and so on without end.

The proof is a short induction. Take the shortest protocol that works and look at its last message. That message might get lost, so the protocol has to succeed without it. Then the shorter protocol already works, which contradicts "shortest." **No finite protocol over a lossy channel guarantees agreement.**

So exactly-once *delivery* can't be done. The industry gets around this instead of solving it: **at-least-once delivery plus an idempotent receiver = exactly-once effect.** Kafka's "exactly-once semantics" (KIP-98, 2017) is this underneath: producer sequence numbers that the broker dedupes, plus transactions. Stripe's idempotency keys are the same idea at the API layer.

**The twist for your ledger:** in gRPC, a `DEADLINE_EXCEEDED` doesn't tell you the transfer failed. The client can't know whether the server committed, which is the Two Generals problem in a status code. That's why the details of the key matter more than having one:
- **Write the key record and the ledger entries in the same DB transaction.** If they commit separately, a crash between the two commits either applies the transfer twice or drops it.
- **Store a hash of the request with the key.** If the same key arrives with a different amount, reject it. Don't replay the old response.
- **Handle a duplicate that arrives while the first request is still running.** Use a unique constraint or row lock on the key and return a conflict. Otherwise two concurrent retries can both get past the "seen this key?" check.
- **Check your gRPC retry policy.** Retries configured in the service config resend requests the server may already have processed, so the server has to dedupe them. Treat any retryable status code as "the server may have committed this."

If your agent's diff does a lookup, then the write, then saves the key as three separate steps, that's the bug to catch in review.

2. **Sideways:** the FLP impossibility result (1985), the other proof every distributed system is quietly working around
3. **Wildcard:** how 1980s tide gauges kept recording through dropped connections, the same problem with seawater
