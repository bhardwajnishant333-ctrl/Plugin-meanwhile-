## Turn 1 — Meanwhile
**The retry that comes back later is the easy case for an idempotency key. The hard one is the duplicate that arrives at the same moment as the original.**

**Mechanism:** The simple version is "look up the key; if it's missing, process the refund and save the result." Two copies of the same request arriving together both find nothing and both refund. The pattern Stripe documents works differently:
- **Claim the key first.** Insert it as an in-flight row before doing any work, and let a unique constraint decide the winner (`INSERT ... ON CONFLICT DO NOTHING`, then check rows affected). The loser gets a conflict response instead of running the refund too. Stripe returns 409 in this case.
- **Store a fingerprint of the request** (a hash of amount, charge ID and currency) next to the key. If the same key comes back with different parameters, reject it instead of replaying the old response.
- **Save the final response on the key row,** ideally in the same transaction as the refund write, so a replay returns exactly what the first call returned.

gRPC makes this more pressing. Its retry design (gRFC A6) includes **hedging**, which deliberately sends several copies of the same RPC in parallel and keeps the first answer. That is simultaneous duplicates by design. I'm fairly sure grpc-go implements retries but not hedging, while grpc-java does both. Check which clients call your service before relying on that.

**Twist:** The fingerprint is the part people skip, and leaving it out fails silently. Picture a client bug that reuses a key from a $5 refund on a $50 refund. Without the fingerprint you return the cached $5 success, the caller records $50 as refunded, and nothing errors. It turns up later in reconciliation. That's worth checking in what your agent writes.

## Turn 2 — Meanwhile
**A key that says "in flight" can't tell you whether the process holding it is still working or has crashed.**

**Mechanism:** Brandur Leach, then at Stripe, described the standard approach in his 2017 post "Implementing Stripe-like Idempotency Keys in Postgres":
- **Split the request into atomic phases** and record a `recovery_point` on the key row after each one (for example `started`, then `refund_created`, then `finished`). A retry resumes from the last recovery point instead of starting over.
- **Lock with a timestamp.** Set `locked_at` when you claim the key. If a retry finds a lock older than a set timeout, it may take the key over.
- **Run a background completer** that pushes abandoned keys forward, and a reaper that deletes keys past their retention period.

The awkward phase is the call out to your processor or card network. That is state you don't own and can't roll back with a database transaction. The usual rule is to derive a downstream idempotency key from yours and send it on every attempt. If the processor doesn't support one, look up the refund there before retrying anything.

**Twist:** The takeover timeout is a correctness setting, not just tuning. Suppose it's shorter than your slowest real request, including the downstream call's own timeout. Then a retry takes over a key whose original handler is still running, and you get two refunds even though you implemented idempotency. The fix is a **fencing token**: increment a version number on every takeover, and make the final write conditional on that version (`UPDATE ... WHERE version = $n`). A handler that has been taken over then fails its write instead of overwriting the newer attempt's result. In Go, set the lease longer than your `context` deadline on the outbound call, never shorter.

1) **Deeper**: fencing tokens in general, and Kleppmann's 2016 critique of Redis's Redlock, which turns on exactly this point
2) **Sideways**: the Two Generals problem, and why exactly-once delivery is impossible while exactly-once effect isn't
3) **Wildcard**: the bar-tailed godwit's non-stop flight from Alaska to Tasmania
